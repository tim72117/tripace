# 構想 3（新手旅行者提出）：沒有座標的行程項目，新手根本看不出風險——逐輪原始稿

> 仲裁後的結論見主文件 `AI_TRIP_PLANNING_DISCUSSION.md` 構想 3 段落，這裡是完整逐輪過程。

**新手旅行者（開場）**：我讀了文件開頭的技術現況錨點，`trip_entry_add`
寫進去的項目只有 `title/date/time/note`，完全沒有座標——這代表 AI 幫我
排的「地點」，跟地圖上真實的位置是斷開的。如果我照著這份行程走，到了
現場才發現「note 寫的地址」跟「AI 以為的順路關係」對不上，這種落差
對新手來說是最可怕的，因為我根本沒有能力事先發現這個斷層——我會直接
相信畫面上排得整整齊齊的時段表。我要的是：只要一個項目沒有座標，介面
上要有非常明顯的視覺警示，不能只是小字註記，要讓我在規劃階段就意識到
「這格是文字承諾、不是地圖上驗證過的地點」。

**老手旅行者**：這個問題我完全同意存在，但我要指出一個更深的根源——
這不是「警示做得夠不夠明顯」能解決的表面問題，是 `trip_entry_add` 這個
工具本身的 schema 缺欄位。就算警示做得再顯眼，AI 產出的東西還是「文字
承諾」，警示只是讓使用者知道有問題，不會讓問題消失。我認為與其在 UI
上堆警示，不如先問：AI 用 `recommend_nearby` 查到的候選地點明明有
座標（`geo.Search`/`SearchNearby` 的結果本來就帶經緯度），如果排進
行程的來源就是這些查到的候選，座標理論上是能傳過去的——問題出在
`trip_entry_add` 這個寫入介面本身沒有座標欄位承接，不是 AI 沒有座標
資料可以用。

**行程規劃師**：老手指出的這個區分很重要，我幫忙釐清成兩種情境，因為
這會影響警示該怎麼設計：情境一是「AI 排的項目來自 `recommend_nearby`
查到的真實候選」——這種項目座標資料其實存在，只是現在的寫入路徑
（`trip_entry_add`）接不住，屬於**可修的資料流斷層**；情境二是「AI
根據使用者描述憑空推薦的地點（例如使用者說『找間好吃的拉麵店』，AI
沒有實際查詢就直接寫進行程）」——這種項目連座標資料源頭都不存在，
屬於**沒有查證過的純文字建議**，跟情境一的風險等級完全不同。如果
把兩種情況都用同一種警示呈現，使用者反而學不會分辨哪種比較危險。

**新手旅行者**：這個區分我認同，而且對我來說反而更清楚——情境一是
「資料在，只是還沒接上」，情境二是「資料根本不存在」，後者顯然該有
更強烈的警示。但我想確認一件事：這份文件的範疇是設計判斷、不是實作
規劃（文件開頭寫明的），那我們是不是不該具體討論「怎麼修 `trip_entry_add`
的 schema」，只該定義「這兩種情境在使用者體驗上該長怎樣」？

**行程規劃師**：對，這個範疇界線抓得對，我收斂一下。設計層面的結論
應該是：AI 產出的每個行程項目都要標明**座標來源等級**——「已驗證座標
（來自查詢工具，只是尚未打通寫入路徑）」與「未驗證推薦（AI 憑描述
生成，未經地點查詢）」是兩種不同等級的警示，等級越低警示要越顯眼、
且不該讓使用者誤以為它跟已驗證的項目同樣可靠。至於 `trip_entry_add`
座標欄位缺失這個資料流斷層本身該不該修、怎麼修，那是實作問題，超出
這份文件範疇，但我認為值得記一筆「這是本討論發現、但故意不展開」的
待辦事項，避免之後被忘記。

**老手旅行者**：同意這個分級設計，也同意不在這裡展開實作细節。我要
額外強調一點跟構想 1、2 呼應：這個「座標來源等級」標示，本質上也是
「不確定性標示」的一種，應該跟前兩項共用的標示語彙系統整合，不要
又獨立出第三套符號——目前累積下來，這套標示系統要能同時表達「內容
本身確不確定」（構想 1）、「排序理由可不可信」（構想 2）、「座標
有沒有驗證過」（構想 3），這已經是一個需要統一設計的完整機制，不是
三個各自獨立的小提示。

**仲裁結論**：三方共識——AI 產出的行程項目必須標示**座標來源等級**，
區分「已驗證座標（源自 `recommend_nearby` 等查詢工具，僅受限於
`trip_entry_add` 目前的寫入路徑未承接座標欄位）」與「未驗證推薦（AI
憑使用者描述直接生成，未經任何地點查詢）」兩種等級，後者風險更高、
警示需更顯眼，不可與前者用相同視覺權重呈現。`trip_entry_add` 的 schema
是否/如何補上座標欄位屬於實作範疇，本文件不展開，但記錄為本討論
發現的待辦缺口。此外三方一致認為，構想 1（不確定性標示）、構想 2
（排序理由可信邊界）、構想 3（座標來源等級）三者呈現的都是同一種
「AI 表述可信度分級」機制，應設計成同一套共用的標示語彙，不應拆成
三套獨立符號系統——這點會在收尾總結中作為跨構想規律再次提出。
