## 核心問題

AI 現在排行程時，是把一堆單獨的景點（entry）丟進時間軸，靠座標距離跟營業時間湊出合理順序。這種做法對「景點彼此沒有強烈地理關聯」的情境沒問題，但對某些旅遊型態——沿著一條溪流、一段海岸線、一條老街、一條花東縱谷的脈絡——這種「順著走」本身就是體驗的一部分，單點湊順序湊不出這種感覺。

現有的「路徑」功能（`web/src/pace/PaceRouteMap.tsx` + `server/internal/api/pace_route.go`）已經證明「給一批有座標的點，串 Google Routes API 算出一條沿真實路網走的路徑」這件事能做。但它目前只是配速表的輔助視覺（畫出使用者已經排好的行程點之間怎麼走），路徑本身不是一個可以被預先定義、命名、重複使用的實體——這正是構想七要補的缺口：把「路徑」從「行程排完後才算出來的衍生結果」，升級成「AI 排行程前就可以參考、甚至直接套用的既有資料」。

## 不同使用者角度

**第一次規劃某條知名路線的旅客**——例如「花東縱谷自行車道」「九份老街到金瓜石」「台南孔廟文化園區周邊」，這類路線本身已經是被廣泛認可的「一條路」，旅客想要的不是 AI 幫他從頭發明一條路，而是「照這條大家都走的路，幫我排出合理的停靠點與時間」。延伸做法：AI 對話一開始偵測到使用者提及的地點落在某條已登記的路徑範圍內，主動提議「要不要參考『花東縱谷自行車道』這條路徑安排？」，而不是從零開始規劃。

**想要「沿途隨興停」而非精確時間表的旅客**——這類旅客的心理模型更接近「開車/騎車上路，看到喜歡的就停」，而不是逐站打卡。延伸做法：路徑底下掛的「主題點」用構想三討論過的 children 概念呈現——整條路徑本身是地圖上一條線，沿線標出幾個主題點（不是精確到幾點幾分的時間軸節點），每個主題點底下才是具體子景點，使用者可以選擇展開看細節，也可以整段忽略，不強迫逐站規劃。

**內容創作者/部落客（對接構想五）**——部落客寫過「花東縱谷三天兩夜」這類圖文並茂的路線遊記，這篇文章本身蘊含了「這條路徑該怎麼玩」的第一手經驗，比系統自己演算的路徑更有說服力。延伸做法：路徑資料可以反向連結到一篇已發布的部落格文章，AI 排行程參考這條路徑時，順勢把文章裡的圖文素材也帶進使用者看到的行程畫面——詳見下方「前端介面層構想」的照片呈現兩種可能性。

## 資料結構草案

路徑（`RoutePath`，暫定名稱）需要能表達「一條具名的路線」，並且能掛多個主題點，對齊既有的主題點/子景點概念（`web/src/plan-core/planTimeline.ts` 的 `PlanThemeChild`，見該檔案說明：「鄰近的景點不用每個都安排時間點，而是集合的概念」），而不是另外發明一套平行的資料模型：

```ts
interface RoutePath {
  id: string
  name: string              // 「花東縱谷自行車道」「九份金瓜石老街線」
  desc?: string             // 這條路徑適合誰、適合什麼心情走
  waypoints: RouteWaypoint[]        // 途經點序列,決定線怎麼畫
  themePoints?: RouteThemePoint[]   // 沿線的主題點(可選,見下方)
  suggestedDays?: number             // 建議天數(走完整條路大致需要幾天)
  travelModes?: ('walk' | 'bike' | 'drive' | 'transit')[]  // 適合的交通方式
  sourceBlogPostId?: string  // 若這條路徑是從某篇部落格文章萃取/連結而來
  encodedPolyline?: string   // 快取 Google Routes API 算出的路徑線(對齊
                              // PaceRouteMap.tsx 的 RouteCache.encoded)
}

interface RouteWaypoint {
  lat: number
  lng: number
  label?: string             // 給 Routes API intermediates 用的輔助標籤
}

// RouteThemePoint 直接複用 PlanThemeChild 的欄位子集概念——一條路徑上
// 掛的「主題點」跟時間軸上的主題節點是同一種展示單位,只是容器從「時間
// 軸節點」換成「路徑上的一個定錨點」。
interface RouteThemePoint {
  id: string
  name?: string
  desc?: string
  placeId?: string
  lat?: number
  lng?: number
  googlePhotoUrls?: string[]
  children?: PlanThemeChild[]  // 這個主題點底下還可以再掛多個子景點,
                                 // 完全沿用既有型別,不重新定義
}
```

關鍵設計決定：**一條路徑底下能掛多個主題點，一個主題點底下又能掛多個子景點**——三層結構（路徑 → 主題點 → 子景點）對應「這條路線 → 沿途幾個值得停的區域 → 每個區域裡具體的景點」這個自然的心智模型。AI 排行程時可以選擇在「主題點」這一層粒度安排（整個區域排一個時段），也可以下探到「子景點」這一層（區域裡特定幾個點各自安排），彈性留給排程邏輯決定，不是資料結構本身的限制。

## 後端角度

路徑計算沿用既有的 `computeRouteByWaypoints()`（`server/internal/api/pace_route.go`）——給 `RoutePath.waypoints` 當 origin/intermediates/destination，一樣打 Google Routes API 算出 `encodedPolyline` 與每段 leg 的起訖座標，計算邏輯不需要重新發明，只是輸入來源從「使用者行程裡的 entry 座標」換成「路徑自己登記的固定途經點」。

路徑資料存放與發布，可以比照部落格 `content_pages` 那套模式：路徑本身是一種內容型態，由內部 CLI 建立/編輯/發布（不透過一般使用者介面寫入），存進資料庫一張 `route_paths` 表，`themePoints`/`children` 這類巢狀結構用 JSON 欄位存放（對齊 content_pages 的 JSON 內容區塊模式，不用把每一層都拆成獨立的關聯表）。CLI 指令大致是 `cli route-path create/update/publish` 這個方向，細節（欄位驗證、草稿/發布狀態機）留到實際要做的時候再比照 content_pages CLI 的既有慣例展開，這裡先點出「不是全新一套系統，是同一套內容發布模式的另一種內容型態」這個方向即可。

AI 排行程時怎麼「參考」路徑：路徑資料本身可以當作 LLM 工具呼叫的一種查詢結果（類似現有的 attractionTools.ts 查詢機制），例如新增一個 `find_route_path` 工具，依使用者提及的地區/關鍵字找出匹配的已登記路徑，回傳給 LLM 當作排程的參考骨架，而不是要 LLM 自己憑空想像一條路徑該怎麼走。

## 前端介面層構想：使用者會看到什麼畫面

這一節不寫規格條列，試著描繪使用者實際會看到、會點、會停下來多看一眼的畫面（Fable 風格發想，對應 `web/showcase-demo/src/RoutePathPlanningPage.tsx` 的視覺化版本）。

### 場景一：AI 提議一條路徑

使用者在對話框打了「想去花蓮玩三天，喜歡騎腳踏車」。AI 的回覆不是立刻條列景點，而是先彈出一張橫向捲動的「路徑卡」——卡片上半是一張小地圖縮圖，一條淺棕色的線沿著河岸蜿蜒，線上標著三、四個半透明的圓點；卡片下半寫著「花東縱谷平地森林自行車道・建議 2 天・適合單車／步行」。卡片右下角一顆按鈕：「套用這條路徑規劃」。使用者一看就懂——這不是 AI 臨時編的，是一條真實存在、被很多人走過的路，他只是在選一條已經鋪好的路，不是從一張空白地圖開始。

### 場景二：沿途主題點的呈現——地圖為版面骨架

套用路徑後，畫面主體換成一張大地圖，那條路徑線沿著畫面斜切而過，像一條緞帶。線上每隔一段距離浮著一個圓形縮圖徽章（不是普通的 pin 圖釘，是裁成圓形、帶白色邊框的小照片縮圖，像 Google 地圖「熱門景點」標記的質感），點進去才展開成完整卡片。這個版面選擇是刻意的：地圖是主角，照片是點綴在路徑上的「預告」，使用者的視線動線是先看到整條路的形狀，再被某個縮圖吸引去點開細看——而不是先看一排密密麻麻的文字清單。

### 照片呈現：兩種可能性

點開路徑線上的某個主題點縮圖，畫面會往下展開一張卡片——這張卡片長什麼樣子，取決於這個主題點的照片來源是哪一種：

**可能性 A・Google Places 相片**：卡片展開後是一排可以左右滑動的照片，畫質偏「寫實紀錄」——遊客自己上傳到 Google 的隨拍，可能某張角度有點歪、某張人臉被打了馬賽克，但正是這種「不完美的真實感」讓使用者覺得「這是真的有人去過、拍下來的」。照片下方一行小字：「來自 Google 地圖使用者相片」，旁邊一個小小的 Google 標誌，誠實標示來源。這組照片配的文案很短——一兩句話描述這個主題點是什麼、大概要停多久，語氣像導覽手冊的簡介，不是散文。這種呈現適合「系統自動從路徑途經點抓出來的主題點」，沒有人特別為它寫過文章，照片是唯一能快速建立畫面感的素材。

**可能性 B・連結既有部落格文章**：卡片展開後完全是另一種質感——不是零散的隨拍，而是一張精心挑選的大圖置頂（部落格文章裡的封面或代表圖），底下接著一段摘錄的文字，字體換成文章慣用的襯線風格，像在讀一段遊記節錄而不是系統生成的介紹。卡片右上角一個小標籤「摘自：〈花東縱谷騎行兩日記〉」，點擊可以直接跳轉到完整文章。往下滑，如果這篇文章裡本來就有一組多圖排列（對齊既有 `content_pages` 的多圖群組排版），這裡會直接重用同一組圖文，不是重新裁切或重新上傳——使用者感覺像是「AI 幫我把某個部落客寫過的真實體驗，直接搬進我自己的行程裡」，照片跟文字是同一個人、同一次旅程的產物，敘事是連貫的，不是東拼西湊。這種呈現適合「使用者選用的路徑本身就是從某篇文章萃取而來」（對齊上方資料結構草案的 `sourceBlogPostId`），這條路徑跟那篇文章本來就是血緣關係，呈現時理所當然要讓這個血緣可見。

兩種可能性不是互斥的二選一——同一條路徑上，有文章紀錄的主題點用可能性 B 呈現，沒有文章只有 Google 資料的主題點用可能性 A 呈現，使用者在同一張地圖上滑動瀏覽時，會自然遇到兩種質感交替出現：有的停靠點像導覽手冊的簡介卡，有的停靠點像翻開一頁別人寫的遊記。這種交替本身不是缺陷，反而讓整條路徑讀起來有層次——系統補完的資訊跟真人寫過的體驗並存，使用者可以憑直覺分辨「這段是有人真心推薦過的」還是「這段是系統幫我查到的基本資訊」。

### 場景三：AI 排程時「借用」路徑的語氣

使用者套用路徑後繼續跟 AI 對話：「那在這附近找個地方吃午餐」。AI 的回覆會順勢提到「沿著這條路徑，大約在你們第一天行程的中段會經過『大富火車站』附近，那邊有幾間老店」——AI 說話時明確知道「使用者現在是沿著這條路徑走」，推薦邏輯錨定在路徑的地理脈絡上，不是憑空丟一個離題的建議。這呼應核心問題：路徑不只是畫面上的一條線，也是 AI 回話時隱含的「我們現在正走在哪」的上下文。
