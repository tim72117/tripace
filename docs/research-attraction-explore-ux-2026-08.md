# 景點延伸探索（Attraction Explore）操作流程與介面設計研究

> `research-*` 一次性研究快照（2026-08-30）。若後續定案要實作，另開 `refactor-*` 規劃承接，本文保留不動。

## 1. 背景與現況

規劃地圖（geo-outline）目前的「探索周邊」（`AttractionInfoPanel.tsx:82` → `DesktopLayout.tsx handleExploreAttraction`）只做兩件事：地圖 fitBounds 到景點區域範圍、查詢附近地點倒進**平面清單**（GeoHotelSidebar / 手機版地點清單 sheet）。使用者看到的是一串同質卡片——沒有表達「這些地點跟你正在看的景點是什麼關係」「哪些是有特色的、值得繞過去的」，探索的樂趣與決策線索都被壓扁成一維列表。

既有資料基礎：`GeoAttraction`（name/lat/lng/placeCount/landmarkPhotoUrl/radiusMeters）、`GeoSearchResult` 合併清單、`fetchGeoPlacesNearby`（類別查詢）、候選籃/排期（`useGeoPlanningState`）、多層 bottom sheet 堆疊框架（`useSheetStack` + `PhoneBottomSheet` 三段式吸附）。

## 2. 設計目標與使用者情境

**目標**：使用者停在某個景點（錨點）時，能以「關聯」為線索延伸探索周邊有特色的地景、必吃餐廳、店家、旅館——每個推薦都要回答「**為什麼跟這裡有關**」「**為什麼值得**」，而不是「剛好在附近」。

**情境走查**：
1. 小芸在規劃京都行，點了地圖上的「清水寺」光暈 → 資訊卡出現。
2. 她按「延伸探索」→ 進入探索模式：畫面以清水寺為錨點，周邊有特色的項目以「關聯」方式視覺化呈現（不是平面清單）。
3. 每個項目帶**關聯理由**（「順路——參道下坡 6 分鐘」「在地必吃——湯豆腐百年老店」「拍照地景——八坂塔街景」）與**特色標記**（百年老店/在地人推/絕景/隱藏版）。
4. 她點其中一項 → 資訊卡疊上來（沿用既有 sheet 堆疊）→「加入候選」或繼續從**這個新錨點**再延伸（探索鏈）。
5. 退出探索模式回到一般地圖瀏覽，候選籃已收集了這一串發現。

**設計原則**（對齊 `frontend-design-guidelines`）：
- 關聯要「看得見」：連線/距離/類別用視覺編碼，不靠文字堆疊。
- 一次呈現 5–8 項精選，不是 20 筆撈回來全丟——「有特色」靠後端排序策略（見 §7），前端只負責讓精選看起來值得。
- 探索是疊加模式不是換頁：地圖仍在底層，退出即回原狀（沿用「地圖常駐、內容疊加」的既有架構）。
- 每一步都能收斂到既有動作：加入候選/排日期，不另發明新的收藏系統。

## 3. 操作流程

```
一般瀏覽                探索模式                     深入單項
─────────              ─────────                   ─────────
點景點光暈/marker   →   資訊卡[延伸探索] 按下
                        ├ 地圖鏡頭拉到錨點區域
                        ├ 關聯視覺層疊加(§5 擇一為主方案)
                        ├ 類別篩選(全部/地景/餐廳/店家/旅館)
                        │
                        點某個關聯項目          →   資訊卡疊上(既有 sheet 堆疊)
                        │                           ├ 關聯理由 + 特色標記
                        │                           ├ [加入候選] [排日期]
                        │                           └ [從這裡延伸] → 錨點切換,探索鏈+1
                        │
                        關閉(× / 下滑 / 點地圖空白處) → 回一般瀏覽
```

**入口**：
- 資訊卡（`AttractionInfoPanel` / `GeoOutlinePhoneInfoSheet`）的「探索周邊」升級為「延伸探索」——不再只是 fitBounds，而是進入探索模式。
- 地圖長按任意點（第二階段）：以按壓點為虛擬錨點探索。

**探索鏈（breadcrumb）**：從 A 延伸到 B、再從 B 延伸——頂部顯示麵包屑「清水寺 › 八坂塔 › …」，點任一節可跳回；退出時整鏈路徑可一鍵「全部加入候選」。這是本功能跟平面清單最大的差異化：探索變成有記憶的路徑，而不是每次歸零的搜尋。

**手機版**：探索層以半版 sheet（中段吸附）呈現、地圖仍可見可拖；桌面版以錨點側欄 + 地圖疊加層並存。

## 4. 關聯資料模型

每個推薦項目除了既有 `GeoSearchResult` 欄位，需要：

| 欄位 | 說明 | 範例 |
|---|---|---|
| `relationKind` | 關聯類型 | `on-the-way`（順路）/`local-must`（在地必吃必買）/`scenery`（地景/拍照點）/`stay`（住宿圈）/`same-theme`（同主題延伸） |
| `relationReason` | 一句話關聯理由（LLM 生成或人工建檔） | 「參道下坡步行 6 分鐘，回程順路」 |
| `traits` | 特色標記（最多 2 個） | 百年老店/在地人推/絕景/隱藏版/晨型/夜間點燈 |
| `walkMinutes` | 從錨點步行分鐘 | 6 |
| `affinity` | 關聯強度 0–1（排序與視覺權重用） | 0.85 |

## 5. 關聯的視覺表達方式構想

七個方向，各自的隱喻、優缺點與適用場景。原型驗證見 §9。

### A. 星座連線（Constellation）——主推
地圖（或風格化底圖）上錨點發光，關聯項目以光點呈現在**真實相對位置**，細線連回錨點；線上掛關聯理由膠囊，線的粗細=關聯強度，顏色=類別。
- ✅ 保留地理真實性（距離方向可信）、「探索」的浪漫隱喻強、跟現有地圖光暈視覺語言（radial-gradient halo）同族。
- ✅ 探索鏈自然延伸：新錨點點亮、舊連線退為餘暉，路徑像星圖被逐步畫出。
- ⚠️ 項目密集時連線交錯；需限制同屏 ≤8 項並做避讓。

### B. 軌道環（Orbit）——類別總覽輔助
錨點居中，四條同心軌道由內而外＝地景/餐廳/店家/旅館，項目以圓形頭像掛在軌道上緩慢公轉；點類別軌道整圈高亮。
- ✅ 類別結構一目了然、視覺記憶點強（星系隱喻）、不依賴地理座標所以永不交錯。
- ⚠️ 犧牲真實方位（軌道位置≠實際方向），需以「步行 X 分」補償距離感；動態公轉要尊重 `prefers-reduced-motion`。
- 適合當「總覽/入口動畫」，點入後切回地圖真實位置。

### C. 順路串珠（Path Beads）
以錨點為起點的建議步行動線，項目像珠子串在路徑上，珠與珠之間標步行分鐘；整條可一鍵加入候選成半日路線。
- ✅ 直接產出可執行的行程片段，決策成本最低；「順路」這個最高頻關聯類型的最自然表達。
- ⚠️ 需要路徑規劃（可先用直線序列近似）；只適合表達線性關聯，餐廳/旅館這類「終點型」項目不適合串。

### D. 主題卡疊（Deck）
關聯項目一次一張大卡（滿版照片+關聯理由+特色標記），左滑跳過/右滑加入候選/上滑看下一類別。
- ✅ 沉浸、單手操作、照片表現力最大化；適合「懶得研究、給我最好的」使用者。
- ⚠️ 完全喪失空間感與總覽；適合當探索模式裡的次級瀏覽模式（從 A/B 切入）。

### E. 光暈距離帶（Ripple）
錨點向外三圈漣漪＝步行 5/10/20 分鐘帶，項目落在對應圈層；圈層即距離語意，免標數字。
- ✅ 距離感最直覺；與既有光暈視覺零成本銜接。
- ⚠️ 只編碼距離、不編碼類別與關聯理由，資訊量不足以獨挑大樑——適合作為 A 的底層輔助（漣漪+連線疊加）。

### F. 故事河流（Story Stream）
直向捲動的敘事流：「上午在清水寺 → 沿參道下坡會遇到 → 午餐拐進這家 → 傍晚從八坂塔看夕陽」，項目嵌在時間敘事裡。
- ✅ 把關聯升級成「一天的故事」，情感帶入最強；LLM 生成敘事的好舞台。
- ⚠️ 內容生成成本高、每次探索都要組敘事；適合第三階段做「探索結果的分享頁」。

### G. 蜂巢分類盤（Hex Wheel）
錨點周圍六格蜂巢＝六個探索方向（吃/買/看/住/拍/走），點格子才展開該類項目。
- ✅ 先選意圖再看項目，避免一次資訊轟炸。
- ⚠️ 多一層點擊；分類先行的心智模型跟「給我驚喜」的探索情緒相反。適合當 A 的類別篩選器造型，不獨立成模式。

### H. 網紅帶路卡（Creator Reel Cards）——資訊的「網紅化」包裝
借用旅遊網紅（IG Stories/Reels）介紹景點的整套敘事語言：**滿版照片 + 大字 hook**（「清水寺走 3 分鐘，在地人才知道的七味老鋪」——關聯理由寫成鉤子句，不是說明句）、**貼紙感資訊標籤**（📍位置・⏱步行分鐘・💰價位帶・📸打卡點，微傾斜疊在照片上）、**「在地人偷偷說」tip 氣泡**（避開人潮時段、必點品項這類只有去過的人知道的細節）、頂部進度點（stories 心智）、點左右切換上/下一個 spot。
- ✅ 這是使用者在社群上**已被訓練過的閱讀模式**——同樣的資訊（關聯理由/特色/距離）包成網紅語氣後，吸引力與可信度感都顯著提升；照片主導讓「有特色」用視覺自證。
- ✅ 與 D（卡疊）天然融合：D 提供互動骨架、H 提供內容包裝。
- ⚠️ 依賴照片品質與 hook 文案生成（LLM 可勝任）；純資訊效率低於清單，適合「逛」不適合「查」。

### I. 一日路線 Vlog 時間軸——C 順路串珠的網紅化
把串珠包上 vlog 的時間敘事骨架：**07:00 清水寺（避開人潮的清晨光）→ 09:30 二年坂 → 12:00 湯豆腐午膳…**，每站帶「必拍 📸」「必點」callout 與網紅口吻的一句話，站與站之間標步行分鐘，結尾「這條路線整天走下來——一鍵全部加入候選」。
- ✅ 網紅「一日路線」是旅遊內容最高轉化的格式；時間軸直接對映 App 的排期模型（date+startTime），加入候選時可連時段一起帶入。
- ⚠️ 敘事生成成本同 F；先做模板化（時段+類別套語）再演進到 LLM 全文。

### 推薦組合
**主方案 A（星座連線）+ E 當底層距離帶 + G 造型化為篩選器**——負責「空間探索」的骨架；**H（網紅帶路卡）當單項內容的呈現層**——星座上點開一個光點，細節不再是乾清單而是一張帶路卡；**I（Vlog 時間軸）當探索鏈的收斂出口**——探索完一串後「整理成一日路線」預覽再入候選。B（軌道環）做進場總覽動畫；D、F 的骨架已被 H、I 吸收，不再獨立實作。

## 6. 介面設計要點

- **探索層是 sheet 堆疊的一員**：進入探索模式＝`sheetStack.push({type:'explore', anchor})`，跟資訊卡/日期選擇共用同一套堆疊心智（FE13 教訓：不要再造遊離 state）。
- **視覺基調（2026-08-30 定向）**：探索功能**刻意跳脫**現有首頁/App 的沉穩紙感，走「貼紙拼貼 × 波普撞色」的活潑識別——向日黃/珊瑚紅/鈷藍/薄荷綠/泡泡粉高飽和色、粗描邊（2–3px ink outline）、硬陰影（4px 4px 0 無模糊）、元素微旋轉、圓體字（Hiragino Maru Gothic/圓體系）、漢字類別貼紙（景/食/買/宿）。理由：探索是 App 裡情緒最接近「玩」的時刻，網紅內容的視覺語言（貼紙、拍立得、紙膠帶、手繪箭頭）本身就是吸引力的一部分；與主 App 的落差反而形成「進入探索模式」的儀式感。實作時以獨立的 token 組（`--explore-*`）承載，不污染主 App 色板；深色模式改深靛藍底、飽和色維持（在暗底上更跳）。
- **色彩**：關聯類別色（餐廳=珊瑚紅、地景=薄荷綠、店家=鈷藍、旅館=泡泡粉），連線/光點皆需深色模式對應 token（吸取 FE16 教訓，一開始就用 CSS 變數）。
- **動態**：連線繪製用 stroke-dashoffset 入場（600ms 內完成），公轉/漣漪一律包 `prefers-reduced-motion` 降級為靜態。
- **空/錯/載入三態**：查無特色項目時顯示「這一帶我們還沒挖到寶——換個景點試試」而非空白；載入用連線逐條點亮當進度表達。
- **點擊目標**：光點含觸控熱區 ≥44px（視覺可小、熱區要夠，吸取 FE19 教訓）。

## 7. 資料與後端需求

1. 新端點 `GET /internal/geo/attractions/{id}/related?limit=8`：回傳帶 `relationKind/relationReason/traits/walkMinutes/affinity` 的精選清單。
2. 「有特色」排序策略：評分×評論數下限過濾 + 類別配額（至少 1 地景 1 餐廳）+ LLM 對 top-N 生成 `relationReason/traits`（可離線批次建檔進 DB，熱門景點預算可控）。
3. 探索鏈不需後端狀態——純前端堆疊，退出時批次寫入候選。
