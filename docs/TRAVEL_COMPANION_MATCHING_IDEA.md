# 新點子:旅伴應徵配對

> 記錄時間:2026-08-14。這是初步構想草稿,尚未進入資料庫/API 設計階段——目的是先把點子的範圍、跟既有功能的關係、待決策項目寫下來,避免討論到一半忘記脈絡。

## 一句話說明

使用者可以選擇一條既有路徑(自己編的或別人發布的推薦路徑),或直接製作一條新的,發布成「應徵旅伴」的貼文,設定想要的旅伴條件;其他使用者瀏覽並提出配對,雙方條件相符時開啟聊天室自行洽談。

## 跟「旅程分享/路徑編輯器」的關係

**建立在路徑之上,不是獨立功能。**

路徑編輯器(見同一輪討論、已試作 artifact 的雜誌式編輯介面)產出的內容本身就是一條「可分享的路徑」;旅伴應徵是這條路徑的**第二種用途**——除了單純分享給人看、被投稿收錄進系統推薦路徑之外,現在還可以附加「我想找人一起走」的招募資訊。

```
路徑(既有構想)
  ├─ 純分享(供他人瀏覽/複製)
  ├─ 投稿審核 → 系統推薦路徑
  └─ 應徵旅伴(新)
        ├─ 附加配對條件
        ├─ 進入配對池
        └─ 配對成功 → 聊天室
```

發起應徵時,使用者從兩個入口選路徑:
1. **選一條既有路徑**——自己之前編過的,或別人已發布、允許被引用的推薦路徑。
2. **當場新建一條**——直接跳進路徑編輯器現場做,做完直接接續發布應徵。

這代表應徵貼文的資料結構,大機率是「路徑 ID + 一組配對條件欄位」的組合,不需要重新設計一套跟路徑無關的行程描述格式。

## 配對條件(使用者可設定/篩選的維度)

三類條件,發起應徵時勾選:

- **基本資料**:年齡層區間、性別(含不限)。
- **旅行風格**:步調(淡定 ↔ 高強度)、預算區間、體驗傾向(例如「行程彈性 vs 按表操課」)——具體選項清單待細部設計時再定,先確定「風格類條件」是獨立於基本資料的一類。
- **行程相關**:日期(區間或彈性範圍,需跟路徑本身若已綁日期時互相檢查是否衝突)、同行人數需求(還缺幾人)。

> 待討論:條件是「發起人設好門檻,應徵者需符合才能提出配對」的**硬性篩選**,還是「發起人設定的是偏好,應徵者條件不同仍可提出、由發起人自行決定要不要接受」的**軟性參考**?這會決定配對邏輯是規則過濾還是純展示排序,先記下來,細部設計時要問清楚。

## 配對流程與成功後動作

初版流程(先做,之後可再擴充):

```
使用者 A 發布應徵(路徑 + 條件)
        ↓
使用者 B 瀏覽配對池,看到 A 的應徵
        ↓
B 提出配對申請(或直接應徵,具體互動待設計)
        ↓
A 確認接受
        ↓
開啟一對一聊天室
        ↓
雙方自行談後續(要不要一起出發、行程怎麼分配等,
系統不介入,不自動合併成共享 Trip)
```

初版**不**做的事(先明確排除,避免範圍蔓延):
- 不自動把配對雙方的行程合併成同一個共享 Trip——見上方流程說明,聊天室談完要不要共用行程規劃工具,是雙方自己的決定,不是系統自動化的一步。
- 不做多人團體配對(先只做一對一),團體揪團是否需要屬於範圍待定的擴充項。
- 不做配對演算法/推薦排序(先做「條件篩選 + 瀏覽」,不是「系統幫你推薦最適合的人」)。

## 待決策項目(下次接續討論時處理)

- 配對條件是硬性篩選還是軟性參考(見上方)。
- 應徵貼文的曝光範圍:公開給所有使用者瀏覽,還是需要先加好友/追蹤才看得到?
- 信任與安全機制:要不要有檢舉、封鎖、身分驗證等級之類的機制——旅伴配對涉及真人見面,安全性比純內容分享的路徑功能更需要謹慎設計,這塊還完全沒討論。
- 資料庫 schema(應徵貼文表、配對申請表、跟路徑表/聊天室既有機制的關聯)。
- 聊天室要新建一套,還是能重用專案裡既有的即時通訊基礎設施(如果有的話,需要先盤點)。
