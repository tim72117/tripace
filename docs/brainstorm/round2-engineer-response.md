# 工程師的回應 —— 看過架構師與旅行愛好者的想法之後

看完架構師跟旅行愛好者兩份文件，先講一個直覺：架構師把我原本零散的 22 個「這樣寫會順」抽象成一條主線——**全域單例是那顆投進水面的石頭**。這個框架我認同，而且它比我自己「附註」寫的「去全域化」講得更完整。但正因為我是實際要把那些改動 merge 進 `want_pool.go`、把 `w.mu` 拔掉的人，有些地方我想潑一點冷水，也有些地方我看了才發現「對，這個從技術上還真需要某個能力」。

## 架構師講到我沒想到的點

**第 22 點「無狀態化以契合 Cloud Run」是我漏掉的一整個維度。** 我原本所有建議都隱含一個假設：單一長生命週期 process。我在講「per-session pool」「per-request collector」的時候，腦子裡想的是一台機器裡的 goroutine 隔離。架構師點出 Cloud Run 會水平擴展、會冷啟動、會回收閒置實例——這下我原本第 13 點「RequestInteraction 正式化」的整個設計前提就動搖了：**如果一個工具呼叫 block 住等瀏覽器回呼，而那個 pending interaction 的狀態只活在某台實例的記憶體裡，一旦下一個 WS 訊息被 Cloud Run 路由到另一台實例，resolve 就永遠找不到那個 pending call。** 我自刻的 `pendingCalls` 是純 in-memory map，架構師這一戳，等於告訴我「你就算把它收斂到 `orch.RequestInteraction`，只要狀態不外部化，多實例下一樣會壞」。所以我要修正自己第 13 點：光是「正式化 interaction API」不夠，那個 correlation 狀態必須能序列化到外部（Redis），resolve 要能跨實例。這是我原本完全沒放進願望清單的。

**第 12 點「server-injected 當成型別上分開的兩種輸入通道」比我第 12 點更狠。** 我原本只是想把 `SetSessionEnvs` 從「實例級欄位」改成「隨 ctx 傳入」，解掉併發。架構師更進一步說：可信的 server context 跟不可信的 model-provided 參數，應該在**工具簽章的型別上就分開**。這個我認同得不能再認同——因為 prompt injection 是 LLM 系統的頭號威脅，把 channelID 混在一般參數裡、靠「開發者記得別塞進 prompt」根本是定時炸彈。搭配我第 14 點的泛型註冊 `RegisterTool[In, Out]`，其實可以做成 `RegisterTool[Injected, In, Out]` 三個型別參數，injected 那組由 runtime 從 ctx 填、LLM 的 schema 裡根本看不到它。這是我看了才想補的。

## 架構師想得太理想、落地會卡的地方

**第 10 點「抽象層切在工具邏輯 ↔ 執行環境之間、只依賴一個最小 port」——方向對，但那個 port 沒有他講得那麼小。** 架構師說工具只依賴「拿到 tenant/channel context、讀寫 store、回傳結果或掛起」。聽起來很乾淨，但我實際看 `wanttools` 裡的工具：`recommend_nearby` 要打 Google Places、`present_entries` 要 emit 給前端 UI、`trip_entry_add` 要等瀏覽器 WS 回呼。這三個的「執行環境依賴」根本不同構——一個是出站 HTTP、一個是伺服器推前端、一個是雙向 request/response。要用「一個最小 port」把這三種都抽乾淨，那個 port 最後不會小，會長成一個包含「同步回傳 / fire-and-forget 通知 / 掛起等待回呼」三種 return 形態的介面，而且 onagent 的 AgentBridge 是在瀏覽器端跑工具、want 是在後端跑，兩邊對「present_entries 該送去哪」的語義天差地遠。我不是說不能做，而是「最小 port」這個詞會讓人低估它——真做下去，那個 port 的 interaction 半邊會跟第 5 點的非同步模型一樣複雜。

**第 9 點「工具 IR 作為單一真相來源 + 多個轉譯器」——我舉雙手贊成，但要提醒 IR 一定會有洩漏。** 我在 POC 裡踩過的坑很具體：onagent 沒有 `appId` 概念、`kind` 語義跟自家不同、有些擴充欄位對方不支援（這些我第 23 點寫過）。當你要設計一份 IR 同時餵給 want registry 跟 onagent YAML，你會發現有些欄位是某一邊獨有的。IR 若強行只保留交集，會漏掉平台特性；若保留聯集，轉譯器就得處理「這個欄位在目標平台無意義要丟掉、那個要有預設」的一堆 case。這不是反對，是說第 18 點「IR 帶 schema 版本、adapter 啟動時做相容性檢查」會比想像中重要且麻煩——**因為漂移不只發生在「我改了 IR」，也發生在「onagent 平台自己升級改了它接受的 schema」，那是我控制不了的第三方**。啟動時 fail fast 我完全同意，但這件事的複雜度架構師低估了。

**第 3 點「per-tenant quota、背壓」我要補一個現實：配額要有意義，得先有身分。** 架構師說匿名公開連結持續打字就是 DoS 面，engine 要 per-tenant quota。技術上對，但「tenant」對一個免登入公開分享連結是什麼？沒有登入就沒有穩定 tenant id，你只能退回用 channelID 或 IP 當配額鍵——channelID 可被同一個匿名連結的多人共用、IP 在 NAT 後面會誤傷。所以「框架提供 quota 旋鈕」是必要條件但不是充分條件，應用層還是得決定「拿什麼當 key」，而這個 key 的選擇本身有安全與體驗的取捨。框架給我 `MaxConcurrentInferences` 跟佇列（我第 3 點要的）我很開心，但別讓人以為 quota 一開就自動安全。

## 旅行愛好者讓我「啊，這個技術上真的需要 XXX」的地方

旅行愛好者這份最有價值的是——**他把我抽象的技術建議，翻譯成了具體的失敗場景，讓我反過來驗證我的建議夠不夠。**

- **第 5 點「一群人同時講話，AI 不要排隊一個一個回」——這根本就是我第 2 點 mutex 的使用者側證詞。** 我寫「同時只有一個人能跟 AI 講話」是工程描述，他寫的是畢旅群組七八個人丟訊息卡住的實際體感。這兩個是同一件事的兩面，看了很爽，代表我砍 `w.mu` 的優先級沒有排錯。

- **第 16 點「我可以直接跟它說『你記錯了』，它會改過來還會記住」——這個看了我才意識到我的建議清單裡缺一塊。** 「當場改好」我的工具能做（就是一次 mutation）。但「下次還記得別再犯」是**跨 session 的持久化偏好記憶**，這在我整份文件裡完全沒有對應的技術建議——我講的全是單輪推論的生命週期、併發、可觀測性，沒有一條講「使用者級的長期記憶 store」。他這一句逼我承認：要做到「越用越懂我」，光有 `want` 的 orchestrator 不夠，得在工具層外面加一個 per-user 的 preference/correction store，而且要能在組 prompt 時把這些 correction 當 context 餵進去。這是架構層級的新東西，不是 `want` 的 API 補一補就有的。

- **第 18 點「分享連結設定幾天後自動失效」——技術上不難，但它跟架構師第 13 點的 capability 是同一件事。** 旅行愛好者要的是 UX（過期自動作廢、我不用記得回去關），但落地就是「連結帶一個 signed、有 exp 的 token，公開 session 只綁 read-only capability」。架構師講「匿名 session 只能拿 read-only capability」是抽象原則，旅行愛好者的「暫時給某人看一下、過期關掉」是那個原則的具體 UI。這兩份文件在這裡漂亮地對上了，我原本第 30 點只想到「工具層授權要把 channel scope 綁在憑證上」，沒想到憑證還該帶 TTL——這是看了才補的。

## 潑冷水：旅行愛好者有些期待，短期落不了地

- **第 9、10 點「沒網路也要看得到行程 / 改的東西不要弄丟」——這是完整的離線優先架構，不是 `want` 或 `onagent` 能給的。** 這要求前端有 local-first 儲存 + 衝突合併（CRDT 之類）+ 重連補傳。我們現在整個工具呼叫模型是「後端跑 LLM、瀏覽器只是 IO」，離線時後端根本不在，AI 一個字都吐不出來。所以老實說：「沒網路看得到今天去哪」勉強可做（把行程快取在本地），但「沒網路還能跟 AI 改行程」在目前架構下做不到，得誠實跟使用者說離線只有唯讀。

- **第 3 點「兩人同時改同一筆、不要互相蓋掉」——這是分散式並行寫入的老難題，跟 AI 無關。** 架構師第 4、22 點把狀態外部化之後，這才有得談（樂觀鎖 / 版本號 / 衝突提示）。但它跟「AI 助理」是兩回事，是底層資料層要解的。我想提醒的是別把它包裝成「AI 能幫你喬」，它本質是 last-write-wins 要換成 conflict-aware 寫入，是 DB 層工程，不是 prompt 工程。

## 一句話收尾

架構師給了我一根槓桿（去全域單例）跟一個我漏掉的維度（無狀態化 for Cloud Run），後者直接逼我修正第 13 點的 interaction 設計——**狀態必須外部化，不然多實例下 resolve 會迷路**。旅行愛好者則幫我補了一塊我整份文件都沒碰到的東西：**跨 session 的使用者偏好/更正記憶**，那是「越用越懂我」唯一的技術路徑。我唯一要架構師跟旅行愛好者都留意的是：**IR 的洩漏、匿名 session 的 quota key、以及離線寫入**這三件，聽起來都像「框架補個 API 就好」，但每一件落地都會比文件裡的一句話重得多。
