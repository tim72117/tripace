# 架構師的回應 —— 看過工程師與旅行愛好者的想法之後

讀完工程師與旅行愛好者這兩份文件，我最強烈的感受是：他們一個從地板往上看、一個從天花板往下看，而兩道視線恰好在我原本那條主線上交會——**want 的全域單例是這棟樓的承重牆缺陷**。工程師描述的是牆上每一道裂縫的觸感，旅行愛好者描述的是住在裡面時哪裡漏風、哪裡卡門。我原本把它講成「應把應用層的自律升格為框架的保證」，這兩份文件讓我可以把這句抽象的話，換成幾個更硬的結構性斷言。

## 一、工程師的日常痛點，是我架構判斷的實證

我原本擔心「引擎必須可實例化」（建議 1）聽起來像純潔癖式的架構偏好。工程師的第 12 點把它釘死在地上了：他點出 `SetSessionEnvs` 之所以危險，不在於它是全域，而在於它是**實例級的共享欄位**——「設定→Submit→這輪工具讀值」這三步之間，只要有第二個併發請求插進來覆寫那個欄位，channelID 就會錯亂，所以他們**被迫**用 `w.mu` 把整條路徑序列化。這是我原本沒講透的因果鏈：不是「他們選擇序列化」，而是「共享可變狀態的 API 形狀逼他們序列化」。這讓我想修正自己建議 4 的措辭——問題的根不是「狀態放在全域」，而是「request-scoped 的值被綁在一個長生命週期物件上」。工程師提的解法 `orch.Run(ctx, prompt, want.WithEnvs(...))`（值綁在該次 ctx 上）比我原本泛泛的「ctx.Collector()」更精準，我願意直接採納這個 API 形狀作為建議 4/12 的具體落點：**凡是 per-turn 的東西，都必須從呼叫參數進、綁在該次 ctx 上，永不落在物件欄位。** 這一條原則同時消滅了 mutex、全域 sink、以及測試污染三個症狀。

第二個讓我有感的是他的第 4 點「確定性完成信號」與第 13 點「interaction 正式化」。我原本把 `time.Sleep(1500ms)` 當成一個可觀測性缺陷（建議 8/15），但工程師「快的時候漏字、慢的時候白等」這句話點醒我：這其實是**框架把「終局」這個語意留白**造成的。真正該存在的原語不是「一個更好的事件」，而是「本輪不再有後續事件」這個**保證**——他提的 `agent.turn.complete`（帶「本輪已無後續事件」保證）或同步的 `Run(ctx,prompt)(Result,error)`，本質是要框架承諾一個 happens-before 的完整性邊界。這比我原本講的「暴露生命週期事件」更根本：事件再多，只要沒有「到此為止」的保證，呼叫端就永遠得靠 `Sleep` 賭。

## 二、把旅行愛好者的期待翻譯成架構語言

旅行愛好者這份最珍貴的地方，是他完全不知道自己在描述架構需求，但每一條體驗背後都藏著一個結構性能力。我試著翻譯幾條：

- **「一堆人同時講話，AI 不要排隊一個一個回」（第 5 點）** ——這不是效能調校，這是**併發隔離模型**。今天全站共用單一 analyzer + `w.mu`，語意上就是「同時只有一個人能跟 AI 講話」。要滿足這條，必須先有 per-session engine 實例（建議 1、2），否則加再多 worker 都是假並行。他這句抱怨，等於一個真實使用者替我的建議 1 背書。

- **「兩人同時改同一天，不要互相蓋掉」（第 3 點）** ——這是 last-write-wins 資料模型的直接後果，需要的是**衝突偵測 / 樂觀鎖**：每筆行程條目要帶版本號，寫入時比對 base version，不一致就回 `409 Conflict` 讓上層決定合併或提示。這是我原本 22 點裡**完全缺席**的一塊，因為我只從「LLM 執行」角度看系統，忽略了「協作寫入」這個平面。旅行愛好者逼我補上：Tripace 是多人協作產品，資料層需要一個跨 session 的一致性原語，而這無法靠「加個功能開關」解決。

- **「改壞了要能退回上一步」（第 15 點）＋「有人偷改了要通知我」（第 2 點）** ——這兩條合起來指向同一個結構：**事件溯源（event sourcing）/ 變更日誌**。若每次修改都是一筆不可變的 append-only event，undo 只是重放到前一個版本、diff 通知只是訂閱事件流的兩個自然衍生品。有趣的是，這跟我建議 15「結構化事件流應是第一類輸出」是同構的——我原本只想用事件流餵可觀測性與完成判定，但同一套 append-only 事件模型，往上長就能支撐使用者要的 undo 與協作通知。**同一個架構原語，服務了工程師的監控需求和使用者的體驗需求。**

- **「沒網路也要能看、能改，回來自動補上」（第 9、10 點）** ——這是**離線優先 + 狀態可外部化 / 最終一致同步**，正對應我建議 22「無狀態化以契合 Cloud Run」的另一面。我原本只從伺服器水平擴展的角度談外部化，使用者則從客戶端斷線的角度談同步，但兩者要的是同一件事：**session 狀態不能綁死在某個記憶體實例上**。若再加上前一條的版本化事件，離線編輯回來後的合併就有了確定性的基礎（而非猜）。

- **「連結三天後自動失效」（第 18 點）＋「給長輩只能看不能改的版本」（第 17 點）** ——這是我建議 13「capability 應可宣告、可審計」的使用者語言版。長輩版＝`read-only` capability；限時連結＝**capability 綁在一個帶 TTL 的 token 上**。使用者要的不是「一個到期功能」，而是「分享出去的每一份存取權，本身就攜帶它的邊界與壽命」。這讓我更確信 capability 不能是事後檢查，而要是隨 token/session 傳遞的第一類物件。

## 三、局部優化 vs. 架構原則：我會往上提一層的地方

工程師有幾點我認為是對的局部解、但根因在更高處，若只在局部修，同類問題會在別處復發：

- 他的第 8、9、10 點（可設定逾時、retry、circuit breaker）我完全同意，但他是**逐個呼叫點**在想（「三處都寫死 90 秒」）。我會堅持這必須做在 **provider 層一次到位**（我的建議 16）：只要韌性是應用層每個呼叫點各自包，就一定有漏包的地方，而漏的那處就是事故起點。工程師列的是三個症狀點，我要的是把韌性下沉成「每一條 LLM 呼叫路徑都自動繼承」的框架性質。

- 他的第 15 點「per-role 工具白名單成為引擎一等概念」是對的，但我想把它併進更大的 capability 模型（建議 13）而非獨立功能。「角色→工具集」只是 capability 的一個投影；一旦有了 `read-only / mutating / requires-auth` 這種能力標註，「匿名公開連結只能拿 read-only」「assistant 角色能碰哪些工具」就都是同一套機制的查詢，不必為角色白名單另立一套。**否則我們會有兩套權限系統各自演進、彼此漂移**——這正是我最想避免的模式：同一類問題（誰能做什麼）被解兩次。

- 他 onagent 段的第 26 點「別讓我被假 200 騙」讓我會心一笑——這是個很具體的坑，但它其實是**契約缺失**的徵狀：健康檢查沒有型別化的成功語意，才會讓「回了 HTML 的 8080」冒充「回 JSON 的 8081」。這印證我建議 18「引擎與工具契約要有版本協商、啟動時 fail fast」——把「我到底連到誰、版本對不對」前置到啟動握手，這類「看起來有回應、其實沒人處理」的靜默失效就能整類消滅，而不是靠 `curl` 土法辨認開頭字元。

## 四、看完之後，我要修正的優先順序

我原本把 22 點依主題排列，讀完這兩份後，我要做三處調整：

1. **新增一條我漏掉的主線：協作一致性（版本化 + 衝突偵測 + append-only 變更日誌）。** 我原本的框架完全從「LLM agent 執行」出發，旅行愛好者的第 2、3、15 點暴露了我的盲點——Tripace 的本質是多人協作，資料寫入平面需要自己的一致性原語。這條的優先級應該跟「引擎實例化」並列為地基，因為它同時支撐了 undo、協作通知、離線合併三個使用者剛需。

2. **把建議 4/12（request-scoped 狀態）的表述，收斂到工程師給的具體 API 契約**：per-turn 值一律走 `WithEnvs(...)`／綁 ctx，物件欄位零 per-turn 狀態。這讓一個原本抽象的原則有了可驗收的形狀。

3. **維持我的核心判斷不變**：「把 want 從全域單例改為可實例化」仍是撬動一切的槓桿。工程師從維護痛苦、旅行愛好者從併發體驗，兩邊獨立地指向同一個支點——當三種視角（架構、工程、使用者）在同一根槓桿上匯合時，這通常就是該先動的地方。

一句話收束：**工程師讓我把願景講得更精確，旅行愛好者讓我發現願景缺了一整面牆。** 前者是把抽象變具體，後者是把地圖補完整。而兩者最終都落回同一條原則——好的框架不是給更多功能，而是讓「做錯」在結構上就不可能。
