# 測試/品質保證專家的收斂意見 —— 第二輪

讀完後端工程師與架構師的清單，先講一句守門員的立場：**這兩份清單品質很高，止血點抓得準、地基掛點想得清楚。但它們的共同盲區高度一致 —— 幾乎每一項都在講「做什麼」，極少講「怎麼證明做完之後它真的有效、之後不會被改回去」。** 我的第二輪工作就是把這條縫補起來：把「做了某件事」跟「有證據證明它有效」分開，並主張最終 10 項不能讓測試防線被功能/地基整批擠到後面。

---

## 一、高共識項目：三方都提到，但每一項我都要補一刀「證據呢？」

先確認共識。以下四類三份清單都出現，方向沒有爭議：

- **panic recovery**：工程師 #1、架構師 B1、我 C7 的精神一致。
- **誠實的 /health（DB ping + MigrationOK、liveness/readiness 分開）**：工程師 #2、架構師 A3、我 C10，三方措辭幾乎一字不差。
- **結構化 logging（slog + request/trace id）**：工程師 #3、架構師 A2、我 C11。
- **部署後 smoke test**：工程師 #7、架構師 D1、我 C3。
- **AutoMigrate fail-fast**：工程師 #12、架構師 B6。
- **connection pool 上限**：工程師 #13、架構師 B5。

共識很好，但守門員要追問的是同一句話的四個版本：

1. **panic recovery（#1 / B1）** —— 你補了 recover middleware，**有沒有一個測試證明 panic 真的被接住、process 沒死、而且回了 500？** 工程師 #1 自己點出關鍵：middleware 只保護 HTTP handler goroutine，`sink.go`/`want_analyzer.go` 那 4 個 `go func(){...}()` 不在 handler stack 上。這正是最容易「以為包好了其實沒包」的地方 —— 沒有一條「在背景 goroutine 裡故意 panic → 斷言 process 仍存活、其他請求仍可服務」的測試，這項就是宣稱式安全。**recover 沒有測試守著，比沒 recover 更危險**，因為它給你一種「已經處理了」的錯覺。

2. **誠實的 health（#2 / A3 / C10）** —— 你說要讓 health 反映真實依賴，**有沒有測試證明 DB 掛掉時它真的回非 200？** 這個承諾本身必須被釘住，否則哪天有人重構 handler 把 ping 拿掉，它又默默變回「永遠說謊的 200」，而 smoke test 與 uptime check 全建在這個謊言上。我 C10 已經寫了這兩條測試（正常→200、注入 DB 錯誤/`MigrationOK=false`→503）—— 這不是可選的，這是 smoke test（#7/D1）與 alerting（工程師 #6/架構師 C2）能不能成立的地基。

3. **結構化 logging（#3 / A2 / C11）** —— 三方都在講欄位要齊。守門員的獨立要求（C11 已列）：**欄位要足以把一次線上事故重建成一條測試案例**（who / what / which-entry / which-tool / outcome），而不只是給人看的一行字。如果 log 只是好看但無法回放，觀測與測試的閉環就斷了。

4. **smoke test（#7 / D1 / C3）** —— 三方都說「失敗就別切流量」。但 smoke test 本身也是測試，它會 flaky、會誤報。**誰來守 smoke test？** 這就接到我 C13（flaky 治理）—— 守門員自己爛掉是最隱蔽的失敗模式。

## 二、回應工程師與架構師對「測試項目」的排序

我把兩份清單裡跟測試直接相關的表態抓出來看：

- 工程師：smoke test 是 #7（B 段中段），且註記多處「需搭配測試驗證，跟測試專家清單會重疊」（#9、#15、結尾備註）。**態度是友善的，但把測試當成別人主場的附註，沒有把「CI 接測試」放進自己的前段。**
- 架構師：D1 smoke test 排在最後一段 D，備註更直接寫「B4/D1 會與測試清單交界，架構師立場是價值在無 staging 下的事後偵測，**而非測試覆蓋率本身**」。

**這裡我要據理力爭一件事：兩位都預設「測試 = 覆蓋率」，因此把它當成事後補強。這個框架是錯的。** 在「無 staging、push main 直接 100% 上線、唯一門檻是能編譯過」的現實下，測試防線的第一價值不是覆蓋率，是**攔截**。我 C1（CI gate）的核心論點必須被抬到全清單最前段，理由是它跟兩位的地基項是**乘數關係，不是競爭關係**：

> 現在專案已經有 8 個 Go 測試 + 一條 e2e，但 CI 只做 build/deploy，`go test` 紅了照樣上 prod。這代表你們兩位清單裡任何一項 —— panic recovery、health、connection pool、拆全域鎖 —— **改完之後，沒有任何機制在合併前跑一次測試證明它沒把別的東西改壞**。你們每做一個「立即處理」的改動，都在一個沒有安全網的高空作業。

換句話說：**沒有 C1（CI gate），工程師 #9 和架構師 B7 這種高風險改動本身就是新的靜默失敗來源。** 這不是我在爭測試的地盤，是這兩位的地基項如果沒有 gate 守著，第一次 refactor 就可能悄悄退化而沒人知道。所以 C1 不該排在功能/地基之後 —— 它是讓所有其他項「可以安全地做」的前提。同理 C2（把那條唯一的 e2e 接上 CI）：它是專案裡**唯一**驗證「記事→AI→存檔→顯示整條真的能動」的東西，現在被設計成要手動起三個 process，等於這個唯一守門員永遠不上崗。改 prompt、改工具白名單、改時間欄位壞了 happy path，**兩位清單裡沒有任何一項會抓到**。

## 三、被低估的驗證缺口：這幾項「必須配測試才能安全執行」

這是本輪我最想敲的一段。以下項目三方都在講「要做」，但沒人講「怎麼確認做對了、沒退化」—— 而它們的共同特徵是**改錯了不會 crash，只會靜默壞掉**，屬於測試不守就等於裸奔的高風險區：

1. **拆全域鎖 / 全域狀態序列化（工程師 #9、架構師 B7）** —— 這是全清單風險最高的一項。工程師 #9 自己標 L 並寫「要小心並發正確性」，架構師 B7 更保守地只做護欄不拆單例。**但兩位都沒有配一條並發測試。** 把 `recordMu` + package-level 全域變數改成 per-session struct，最典型的災難就是引入 race condition：測試環境跑一次是綠的，上線多人並發才偶發資料錯亂 —— 這種 bug **改完比不改更危險**，因為它把一個「慢但正確」的系統換成「快但偶爾錯」的系統。**這一項的驗收門檻必須是：`go test -race` 下的並發測試（多 goroutine 同時對不同 channel 送訊息，斷言狀態不互相污染）綠燈，才准合併。** 沒有這條測試，#9/B7 不該被列入「立即處理」—— 或者說，它的「完成定義」必須包含這條測試，否則就是把 race condition 當成功交付。

2. **LLM 完成判定 sleep(1500ms) 改確定性信號（工程師 #11、架構師 B4）** —— 三方都要改。但「改成確定性事件」怎麼證明它比 sleep 好？**必須有一條測試：用 mockllm 精確控制回應時序，讓回應在原本 1500ms 窗口之後才到，斷言它不被截斷。** 我 C7/C9 已經指出可以借 mockllm 控制時序。沒有這條測試，「改好了」只是換了一個沒被驗證的啟發式。架構師 B4 提到 want 內建 `RequestInteraction`/`ResolveInteraction` —— 換用內建機制更需要測試釘住，因為改的是核心流程的完成語意。

3. **entries 多步寫入包交易（工程師 #15）** —— 工程師自己寫「改動需搭配測試驗證」。守門員把話說死：**驗收門檻是一條「注入中途錯誤 → 斷言 DB 維持一致、不留半筆」的原子性測試**（我 C7 已列）。交易這種東西，happy path 永遠是綠的，只有故意讓它中途失敗才驗得出 rollback 真的有效。

4. **時間欄位 字串→timestamptz 遷移（我 C8，兩位未列）** —— 這是**剛完成、風險最集中、且只有一次機會做對**的改動，跑過 prod 就無法重來。目前只有 store 層 trips 有測試，entries 完全裸奔，時區換算與遷移邏輯零測試。兩位的清單完全沒碰這塊，這是三方合起來的一個真實盲點：災難模式是**靜默偏移**（時間差幾小時、全日事件跑出時刻、舊資料日期跑掉），功能不 crash 但每筆行程時間微妙地錯。這項必須進最終清單。

5. **API 授權（我 C4，兩位未列）** —— `internal/api` 810 行、全部授權檢查都在這、**零測試**，程式碼自己都註記了兩個繞過風險（middleware.go:41、api.go:145）。工程師和架構師的清單裡沒有任何一項守「viewer 不能改別人行程」這種靜默越權 —— 而這是「壞掉最貴」的一類。這是三方合起來的第二個明確盲點。

## 四、我的主張：最終 10 項裡，測試/品保至少要佔 3 席

可觀測性與核心穩定性是兩條主線沒錯，但**「怎麼知道穩定性真的被守住」本身需要席次**。我明確主張最終 10 項裡至少這 3 席必須是測試/品保性質：

1. **CI gate（C1）** —— 把現有 8 個 Go 測試 + `vet` + `-race` 接上 push main / PR，設為 branch protection required check。**這是乘數項，不寫一行新測試就讓所有現有與未來測試真的能擋 push。**

2. **唯一 e2e 接上 CI + 核心流程守門（C2，並吸收 C9 確定性層）** —— 讓「記事→AI→存檔→顯示」這條唯一的端到端覆蓋真正站崗，並用 mockllm 把「給定輸入→預期工具序列」寫成 golden 斷言，守住 prompt/工具白名單/dispatch 接線不被改壞。

3. **權限矩陣 + API harness（C4 + C6）** —— 擋掉最貴的靜默越權，同時把 `internal/api` 從「零測試不可能」變成「後續測試便宜」。這一席同時解鎖了工程師 #9/#15 與我 C8 的跨層驗證所需的 harness。

**如果這 3 席被功能/地基擠出前 10，後果很具體：**

- 擠掉 **C1**：兩位清單裡所有改動（含高風險的 #9/B7）都在無安全網下合併，第一次 refactor 引入的靜默退化沒人擋 —— 等於花力氣補地基，卻在補的過程中不斷戳新洞。
- 擠掉 **C2/C9**：改 prompt 或工具白名單弄壞某條路徑（「使用者說刪掉那筆」不再觸發 entry_delete），沒有任何自動化會發現，直到使用者抱怨 —— 正是負責人最怕的靜默失敗。
- 擠掉 **C4**：一次角色比對寫反、一個新 handler 忘掛 require\*，就是靜默越權，不 crash、功能照跑、權限破洞 —— 而且沒有測試意味著下次改動只會讓破洞更多。

我可以接受把 C10（誠實 health）算成「可觀測性」那條主線的席次而非測試席次 —— 它三方共識、成本 S、又是 smoke test 與 alerting 的共同前置，無論算哪條線都該進前 10。但上面那 3 席，是純粹「守門」性質、無法被可觀測性項目替代的。

## 五、補一個三方合起來仍漏的品質盲點

除了前述 C8（時間遷移）與 C4（授權）兩個內容盲點，還有一個**元層面**的盲點三方都沒講：**這些測試防線建起來之後，誰防止它們自己腐化？** smoke test 會 flaky、e2e 有已知時序競態（StrictMode 雙掛載 vs WS handshake，spec 註解裡都記著）、CI retry 會被拿來掩蓋真 flaky。我 C13 主張的 flaky 治理與「必進 gate / 不進 gate」清單分離，不是錦上添花 —— 沒有它，第一次偶發紅燈就會讓團隊開始習慣性 re-run，三個月後 gate 名存實亡，前面所有投入歸零。這一項可以排在前 10 之後，但必須跟 C1/C2 同一批規劃，否則守門員上崗當天就開始生鏽。

**一句話收束守門員立場**：兩位把「系統不要壞」想得很透，我的職責是確保清單同時回答「我們怎麼知道它沒壞、以及改動之後仍然沒壞」。這兩個問題各自需要席次，缺一邊，另一邊遲早悄悄失效。
