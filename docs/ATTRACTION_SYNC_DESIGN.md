# 景點資料同步機制 — 設計討論

## 背景與需求

本機開發環境與正式站各自累積了一些人工建檔的 `attraction`（景點/地標）資料，目前沒有機制讓兩邊的資料保持一致。需要一個工具，讓本機能：

- 把本機新增/修改過的景點資料**推送**到正式站
- 把正式站的景點資料**拉取**回本機

且要像資料庫同步工具那樣，先做**差異比對**（而非盲目覆蓋），確認差異後才真正寫入。

現有資料模型：`model.Attraction`（`server/internal/model/model.go:108-128`）欄位為 `ID`/`Name`/`CityName`/`Lat`/`Lng`/`Level`/`RadiusMeters`/`Summary`/`PhotoURL`/`UpdatedAt`，已有 `UpdatedAt` 但沒有 version/hash 欄位。現有的「同步」機制（`server/internal/api/hub.go` 的 WebSocket 廣播）其實是 invalidate-and-reload：只推「有變動」通知，前端收到後整個重抓，不是欄位級 diff/patch——repo 裡沒有現成的差異比對模式可以直接沿用，這次是全新機制。

## 零、前置檢查：Schema 比對 + 時鐘偏移檢查

在任何比對/傳輸動作之前（比「三層比對」的第零層新鮮度探測還要早），先做兩項健檢，**每次觸發同步都重新檢查一次**（不快取上次的檢查結果）——這兩項檢查本身開銷很小（各一次輕量的 HTTP 請求），用「每次都查」換取「設定變動後不會有一段時間吃到過期的健檢結果」，比額外處理快取失效的時機更簡單可靠。

### Schema 比對

先確認兩邊 `attractions` 表的**欄位集合與型別**是否一致——這是最基本的前提：如果兩邊 schema 不同（例如其中一邊還沒跑過某次 migration，少了欄位或型別不同），後續所有「比對 `UpdatedAt`」「比對欄位內容」的動作都無法保證正確性，寫入時更可能造成資料截斷或型別轉換錯誤而不自知。

- 比對範圍：`attractions` 表本身的欄位名稱與型別（對照 `server/internal/store/entity.go:66-85` 的 `attractionRow`：`id`/`name`/`city_name`/`lat`/`lng`/`level`/`radius_meters`/`summary`/`photo_url`/`created_at`/`updated_at`），不涉及其他表、不比對索引/約束等非資料層面的差異。
- 兩邊欄位集合與型別完全一致才繼續；不一致時直接中止，並列出具體差異（缺少哪個欄位、哪個欄位型別不同），提示需要先讓兩邊的 migration 對齊，不嘗試自動猜測相容性或部分同步。
- 具體怎麼查詢比對兩邊即時的 schema 資訊（例如透過一個新端點回傳欄位結構，或直接查 `information_schema`），留待實作階段確認。

### 時鐘偏移檢查

整套機制大量依賴 `UpdatedAt` 的**跨機器可比較性**（新鮮度探測、交握續傳的斷點查詢都靠比較兩邊的 `UpdatedAt`）——這隱含一個假設：兩台伺服器的系統時間是同步的。若本機開發機時鐘飄移（忘記校時、時區設定錯誤），`UpdatedAt` 的比較結果可能失真，導致「明明有更新卻判定不需要同步」或反之。

- 同步前，本機 server 記錄自己發出請求前的當下時間 `t_local`，向正式站要它當下的伺服器時間 `t_remote`（一次輕量請求），估算兩邊時間差距 `Δ = |t_local - t_remote|`（可再加上請求來回時間的粗略修正，但不必做到 NTP 等級的精確度）。
- `Δ` 超過門檻（門檻值待定，量級上以分鐘計，例如 5 分鐘）就**拒絕同步並警告**，提示使用者檢查本機或正式站的系統時鐘，不嘗試自動修正或忽略誤差繼續執行。
- 現代伺服器/雲端主機通常有 NTP 自動校時、飄移量級在毫秒級，這個檢查預期大多數情況下都會通過；它存在的目的是防呆（例如本機開發機真的忘記校時、或虛擬機時鐘因故大幅漂移），不是常態性的校時機制。

## 一、比對模型：單向指定方向，不做對稱雙向合併

一開始曾考慮過對稱式的雙向比對（`only-in-A`/`only-in-B`/`changed-in-both`/`identical` 四個集合，兩邊互相補齊），但這個模型有個無法單靠「當下兩份清單」解決的根本問題：**只比對兩份當下的快照，無法分辨「這筆是新增的」還是「對方已經刪除、我這邊還留著舊資料」**——這兩種情況攤開來看，「某個 ID 只存在其中一邊」的表徵完全相同，純比對邏輯沒有足夠資訊區分。要解決得額外保存一份「上次同步時的 ID 快照」，但這會讓本機多一份需要維護、可能遺失/過期的狀態。

**改為更簡單、沒有歧義的模型**：每次同步明確指定方向，永遠有一個**來源**（source）跟**目的**（target）：

- `push`：本機是來源，正式站是目的
- `pull`：正式站是來源，本機是目的

同步的語意就是「讓目的方的資料對齊來源方」，比對只算兩個集合：

| 集合 | 定義 | 動作 |
|---|---|---|
| **只在來源方** | 目的方沒有這筆 | 一律新增到目的方 |
| **只在目的方** | 來源方沒有這筆 | 預設**忽略**（保留）；只有加上 `-allow-delete` 才會**從目的方刪除** |
| **兩邊都有、內容相同** | 8 個比對欄位完全一致（見下方） | 不動作 |
| **兩邊都有、內容不同** | 至少一個比對欄位不同 | 用來源方版本覆蓋目的方（單向同步下不需要「比誰新」，來源方就是權威版本） |

這個模型不需要保存任何額外狀態檔——`-allow-delete` 這個顯式旗標取代了原本靠快照才能做的「新增 vs 刪除」判斷：沒帶這個旗標時，「只在目的方」永遠被當成「保留」處理，語意上是安全預設值（不會意外刪資料）。

**比對規則細節**：

- 主鍵：`ID`。
- 參與「內容是否不同」比對的欄位（共 8 個）：`Name`/`CityName`/`Lat`/`Lng`/`Level`/`RadiusMeters`/`Summary`/`PhotoURL`。`PhotoURL` 雖然常是自動查詢帶入的（見 `attraction-update-photo`），仍一視同仁納入比對。
- **`UpdatedAt` 不參與「內容是否不同」的判斷**——GORM 的 `UPDATE` 會無條件更新 `UpdatedAt`，不保證欄位值真的不同，應該用實際欄位內容比對，而不是信任時間戳記。單向同步下 `UpdatedAt` 也不需要用來判斷「誰比較新該贏」（來源方本來就是權威版本），只在差異報告中顯示供人工參考。

### 為什麼不需要衝突解決機制

原本考慮的「兩邊都改過同一筆」衝突情境，是對稱雙向合併模型才會遇到的問題。改成單向、指定方向的模型後，這個情境不存在：來源方永遠是權威版本，目的方的舊內容直接被覆蓋，不需要判斷「誰贏」，也不需要人工介入選擇版本。

先前討論過幾種衝突/同步策略，記錄於此供追溯決策過程，皆已排除：

- **Vector clock / CRDT**：給多節點高頻並發寫入設計（如即時協作編輯），對「兩台自己的伺服器、低頻人工維運」的場景是過度設計。
- **Last-write-wins（比 `UpdatedAt`）+ 人工選擇衝突版本**：對稱雙向模型下的合理折衷，但單向模型下已無「雙方都改過」的情境，用不到。
- **增量同步（時間戳記游標 / CDC 變更日誌）**：attraction 資料量小（幾百到幾千筆量級）、寫入頻率低，全量抓取兩邊資料、逐筆比對即可，不需要給高頻大資料量場景設計的增量機制。

## 二、傳輸流程：dry-run 預設、三層比對降低成本、交握式續傳

### 誰做比對決策：來源方決策，不是本機永遠決策

**比對/決策邏輯由「來源方」（握有權威內容的一方）執行**，不是不管方向都由本機執行——本機永遠是發起 HTTP 請求的一方（架構原則不變，見「三、架構」），但「誰來判斷差異、誰來決定要傳什麼」依方向而不同，且永遠是來源方：

- **push**（本機是來源，正式站是目的）：**本機**是決策方，因為本機是來源方。本機依序向正式站發起第零／一／二層探測請求（見下方三層比對），每一層都是本機主動查詢正式站（目的方）的狀態、自己比對，最後自己決定要推送什麼。
- **pull**（正式站是來源，本機是目的）：**正式站**是決策方，因為正式站是來源方。本機把自己（目的方）的探測結果**送給**正式站的比對端點，由正式站拿這份資料跟自己（來源方）的狀態比對、決定要回傳哪些記錄；本機收到回應後直接寫入，不在本機端執行任何比對判斷。

決策權永遠落在握有權威內容的一方，邏輯是一致的：只有來源方自己知道「我這邊真正的資料長怎樣」，才有能力判斷「目的方缺什麼、跟我不一樣的地方是什麼」。

兩個方向都不會傳送完整資料清單——延續下方三層比對的分層精神，不管哪個方向，都是先送最小的探測資訊，只有判斷「有需要」時才升級到下一層更大量的資料。

**這代表比對邏輯必須寫成兩邊 server 都能執行的共用邏輯**（同一份 Go 程式碼，因為本機與正式站部署的是同一個 `cmd/server` 二進位檔），而不是只存在於「呼叫方」的程式碼路徑裡——pull 情境下，執行比對的是正式站，需要一個新端點讓它接收本機（目的方）送來的探測資料、執行比對、回傳結果（見下方「後端 endpoint」待確認清單）。

### 三層比對：從「要不要比對」到「差異是什麼」逐步加碼

不是每次同步都無條件跑完整比對——比對本身分三層，前一層排除掉「明顯不需要動作」的情況，才進入下一層更昂貴的操作。兩個方向都遵循相同的分層順序，只是「誰發起、誰決策」不同（見上方）：

1. **第零層：新鮮度探測**——決策方（來源方）先取得自己「目前筆數＋最新一筆的 `UpdatedAt` 與 `ID`」（回傳筆數與 ID 是為了在時間戳記剛好相同的邊界情況下，仍能確認雙方看到的「最新一筆」是否真的是同一筆資料），跟「上次同步完成時，目的方最新一筆的 `UpdatedAt`＋`ID`」比較。若來源方自己沒有比目的方記錄更新的資料，直接判定「不需要同步」，結束，連清單都不用拉。
   - `push`：本機（來源＋決策方）直接查詢自己的 DB 取得探測資料；再打正式站（目的方）的探測端點取得目的方現有狀態，本機自行比對。
   - `pull`：本機（目的方）先打正式站（來源＋決策方）的比對端點，並在請求中附上本機自己目前的探測資料（筆數＋最新一筆 UpdatedAt+ID）；正式站收到後，直接查詢自己的 DB 取得來源方探測資料，跟本機送來的目的方狀態比對，並回傳「是否需要繼續」的判定。
2. **第一層：輕量清單比對**——通過第零層才進行，且是分步進行（不是跟第零層一次送完），只有第零層判定「有需要」時，才進一步取得「只含 `ID` + `UpdatedAt`」的完整清單（不含 `Name`/`Summary`/`PhotoURL` 等完整欄位），算出「只在來源方」「只在目的方」兩個集合的**筆數**，以及「兩邊都有」的 ID 交集。
   - `push`：本機（來源＋決策方）向正式站（目的方）要清單，自己比對。
   - `pull`：正式站（來源＋決策方）向本機（目的方）要清單（本機把清單送過去），正式站自己比對。
3. **第二層：完整欄位比對（只對交集部分）**——只針對兩邊都有的 ID，才去抓完整 8 個欄位內容來比對是否相同，把「兩邊都有、內容不同」的實際差異算出來，並附上欄位級的差異內容（例如 `Lat: 25.03 → 25.031`）供人工核對。同樣由決策方（來源方，`push` 時是本機／`pull` 時是正式站）取得所需的完整欄位內容並執行比對。

「上次同步完成時目的方最新一筆的 `UpdatedAt`＋`ID`」哪裡來：見下方「交握式傳輸」——這個值不是另外維護的一份進度記錄，而是每次同步結束時，直接向目的方查詢它當下實際的最新資料狀態，天然保證跟目的方真實情況一致。

Dry-run 報告輸出範例（`push` 情境，通過第零層後）：
```
來源：本機（12 筆）　目的：正式站（10 筆）

將新增到正式站：3 筆
將更新正式站（內容不同）：1 筆
  - lmk_8afe0eb1be4d「清水寺」: Summary 不同、PhotoURL 不同
只在正式站（未帶 -allow-delete，將保留不動）：1 筆

加上 -apply 才會實際寫入。
```

### 交握式傳輸：依時間序傳送，逐筆驗證，筆數核對後才算完成

三層比對結束、決策方（來源方）已經算出「要傳輸哪些記錄」之後，才進入這個階段。實際搬運資料的方向永遠是來源方 → 目的方——這跟「來源方決策」是同一件事的兩面：決策方本來就等於來源方（見上方「誰做比對決策」），不是兩個獨立巧合重疊的角色。

`-apply` 真正執行寫入時，不是把差異一次性整批送過去，而是走一套交握協定，讓中斷後能自然續傳，不需要另外維護一份持久化的進度檔案：

1. 來源方把「本次要傳輸的記錄」依 `UpdatedAt` **由舊到新排序**，把總筆數（N）告知目的方，作為這次傳輸的「應收筆數」。
2. 來源方依排序後的順序（舊→新）**逐筆**傳送。
3. 目的方也依相同順序（舊→新）**逐筆**寫入；**每寫入一筆，立刻回傳寫入結果**（成功／失敗，以及實際寫入的欄位內容），來源方當下就比對這筆的回傳內容是否與送出內容相符（逐筆完整性驗證）。
4. 全部處理完後，目的方回報「實際寫入筆數」，來源方核對是否等於步驟 1 的「應收筆數」：
   - **相符** → 這次同步完成。
   - **不相符**（代表中途斷線、目的方寫入失敗、或連線中斷）→ **不需要猜測斷在哪一筆**，直接重新查詢目的方目前最新一筆的 `UpdatedAt`，用這個值重新跑一次「三層比對」（回到第零層），差異自然只會剩下「目的方還沒收到的部分」，接續傳輸。

**依時間序（舊→新）傳送/寫入是這套機制能夠續傳的關鍵**：因為順序固定、單調遞增，「目的方當下最新一筆的 `UpdatedAt`」天生就等於「已確認同步到這裡」，不需要額外記錄「目前傳到第幾筆」這種容易跟實際寫入狀態脫節的暫存進度——重新查詢一次就能拿到真正可信的斷點，而不是本機自己記得（但可能因為程式異常退出而沒更新）的一份猜測。

## 三、架構：server 對 server，本機永遠是發起方

最初考慮讓 CLI 直接同時持有本機與正式站兩組 token、在客戶端做比對邏輯，但這樣 CLI 需要管理多組認證狀態，結構複雜。改為：

- **CLI 只負責觸發指令、顯示結果**，不直接呼叫兩邊的 API，也不執行任何比對邏輯。
- **比對與資料搬運邏輯放在 server 層，由來源方執行**（見「二、傳輸流程」的「誰做比對決策」）——本機 server 收到 CLI 觸發後，一律主動發起 HTTP 請求去跟正式站的 server 對話；至於比對邏輯實際在本機還是正式站執行，依 `push`/`pull` 而定，兩邊 server 需要共用同一套比對邏輯（同一份 Go 程式碼，因為本機與正式站部署的是同一個 `cmd/server` 二進位檔）。
- 正式站 server 在 `push` 情境下不需要知道「同步」這件事的存在，只是又收到一批帶認證的 `/internal/maintenance/*` 請求；但在 `pull` 情境下，正式站需要執行比對邏輯、主動判斷要回傳什麼，因此正式站確實需要具備「同步比對」這個能力（新端點），不是完全對「同步」無感。

**同步方向與網路發起方向是兩件獨立的事**：無論資料是「推到正式站」還是「從正式站拉回本機」，**發起 HTTP 請求的永遠是本機 server**，正式站永遠是被動接收方，從不主動連線出去——但「誰在請求裡執行比對決策」則依方向而不同（見「二、傳輸流程」）：

| 資料同步方向 | 誰主動發 HTTP 請求 | 誰執行比對決策 | 實際動作 |
|---|---|---|---|
| 本機 → 正式站（push） | 本機 server | 本機（來源） | 本機依序查詢正式站狀態、自行比對，再 `POST`/更新到正式站的 `/internal/maintenance/attractions*` |
| 正式站 → 本機（pull） | 本機 server | 正式站（來源） | 本機把自己的探測/清單資料送給正式站的比對端點，正式站比對後回傳結果，本機依回應寫回本機 DB |

這個設計完全避開了「正式站要如何連到本機 localhost（通常沒有公開網址、在 NAT/防火牆後面）」這個在一般網路拓樸下無解的問題，也不需要引入 ngrok / Cloudflare Tunnel 之類的穿透工具（那會把本機暴露到公網，多一層安全風險）。「發起請求」與「執行決策」是兩個獨立的維度：本機發起請求的角色不變，但請求內容是「查詢＋自行比對」還是「提交資料＋等待對方比對」，依方向而不同。

**背景現況**：目前 CLI 的 `-api` 全域旗標一次只能指定一個目標（`server/cmd/cli/main.go:65-82`），且 token 存放邏輯（`server/cmd/cli/token.go`）是單一固定路徑、不分環境——但採用下方「本機 server 專用 sync-token」的方案後，這個限制不影響本次功能，不需要修改 CLI 既有的 token 機制。

## 四、認證：重用既有的 `login --web` 流程，不新增密鑰

討論過幾種 server-to-server 認證方式：

- ~~OAuth 2.0 Client Credentials Grant~~：業界標準的機器對機器認證流程，但對「只有自己兩台伺服器互相信任」的場景是過度設計（需要維護 token endpoint、client_id/secret 管理、scope 等）。
- ~~固定 shared secret（環境變數）~~：比 OAuth 輕量，但仍需要額外管理一把新密鑰。
- **✅ 採用：重用現有的使用者登入機制。** 正式站的 `/internal/*` 端點本來就已經支援 JWT 認證（就是 CLI `login --web` 用的那套）。讓**本機 server** 走一次這個登入流程，把換到的 JWT 存在本機 server 自己的檔案（例如 `~/.config/tripace/sync-token`，與 CLI 個人登入用的 `token` 檔分開），之後所有同步請求都帶著這把 JWT 呼叫正式站 API。

完全不需要新增資料表/欄位——認證狀態是本機的一個檔案，不是資料庫記錄；正式站不需要知道這個請求來自「同步」還是「一般 CLI 操作」，兩者對它而言無法區分。

流程分兩階段：

- **Phase 1（一次性設定，你手動觸發一次）**：本機 server 開瀏覽器導向正式站的核准頁（重用現有 `login --web` 畫面）→ 你確認授權 → 正式站透過 callback 把 JWT 送回本機 → 本機 server 存進 `sync-token` 檔案。
- **Phase 2（之後每次同步，不需要你再手動介入）**：本機 server 直接讀 `sync-token`，帶著它主動打正式站的 `/internal/maintenance/*` API；若讀不到（尚未設定過），提示先執行設定指令。

詳細流程圖：[認證流程 Artifact](https://claude.ai/code/artifact/d814f2f5-b19e-4320-ad8a-33f3c4e92a70)（Phase 1／Phase 2 的完整請求流程圖示）。

## 五、CLI 指令介面（已確認）

兩個獨立子指令：一次性設定（Phase 1 授權）與實際同步，職責分開，不共用同一組參數。

### 設定：`attraction-sync-setup`

```
tripace-cli attraction-sync-setup -target <正式站 URL>
```

對應「四、認證」的 Phase 1——開瀏覽器導向 `-target` 指定的正式站核准頁（重用 `login --web` 畫面），你確認授權後，正式站透過 callback 把 JWT 送回本機，本機 server 存進 `sync-token` 檔案，同時把 `-target` 網址一併記錄下來，供之後 `attraction-sync` 不需要再重複指定。只需執行一次；`sync-token` 過期或要切換同步對象（例如換一台正式站）時才需要重新執行。

### 同步：`attraction-sync`

```
tripace-cli attraction-sync -direction push|pull [-allow-delete] [-apply] [-retry]
```

- `-direction push|pull`：`push` = 本機（來源）→ 正式站（目的）；`pull` = 正式站（來源）→ 本機（目的）。不需要額外的 `-target <URL>` 旗標——對方網址已在 `attraction-sync-setup` 時記錄下來，不需要每次呼叫都重複指定。
- `-allow-delete`：帶了才會把「只在目的方」的記錄從目的方刪除；預設不帶＝保留（安全預設值，見「一、比對模型」）。
- 預設是 dry-run（只顯示差異報告，不寫入，且只跑到「二、傳輸流程」的三層比對，不進入交握式傳輸）；加上 `-apply` 才會真正執行寫入。
- ~~`-city`（限定只同步某個城市）~~：已移除。第零層新鮮度探測是以「全部資料裡最新一筆 `UpdatedAt`」判斷要不要繼續，若同時支援城市篩選，會出現「篩選城市內其實沒有更新，卻因為別的城市有更新而誤判需要進入完整比對」的問題——篩選範圍會讓新鮮度探測的判斷基準跟實際同步範圍不一致。之後若要重新支援分城市同步，需要一併重新設計新鮮度探測的範圍界定方式。
- `-retry`（選填，僅 `-apply` 時有意義）：強制從目的方目前最新一筆 `UpdatedAt` 重新查詢斷點並續傳——正常情況下，筆數核對不符會**自動**觸發這個流程（見「二、傳輸流程」的交握協定），這個旗標是給使用者手動確認「上次同步中斷了、我要接續」時明確觸發，不需要等下一次自然執行 `attraction-sync` 時才被動偵測到。

## 尚未討論/待確認

依實作階段大致會遇到的順序排列：

1. **`sync-token` 與正式站網址的存放**：檔案路徑、權限、過期/重新授權的處理方式；「記住正式站網址」要存在哪裡（可能與 `sync-token` 同一份設定檔）。
2. **Phase 1 設定流程的 callback 機制**：具體怎麼接，可能可以參考現有 `cli-auth`/`device` 兩條登入落地頁面的實作模式（`server/cmd/cli/main.go` 已有的 `login --web`/`login --device` 邏輯）。
3. **後端需要新增哪些 HTTP endpoint**：
   - **Schema 查詢端點**：供「零、前置檢查」查詢對方 `attractions` 表的欄位/型別結構，具體回傳格式待定。
   - **伺服器時間查詢端點**：供「零、前置檢查」的時鐘偏移檢查取得對方當下時間，具體門檻值（分鐘量級）待定。
   - **第零層探測端點**：回傳「筆數＋最新一筆的 `UpdatedAt`＋`ID`」。
   - **`pull` 專用的比對端點**（新架構下才需要）：接受本機（目的方）送來的探測/清單資料當請求內容，由正式站（來源＋決策方）執行比對邏輯，回傳判定結果／差異內容——`push` 情境下不需要這個端點，因為決策在本機執行，本機只需要依序 `GET` 正式站現有的探測/清單/完整欄位端點即可。
   - 目前 `/internal/maintenance/attractions*`（`server/internal/api/maintenance.go`，路由掛載於 `server/internal/api/api.go:234-239`）只有 add/list/cities/delete/update-photo，**沒有通用的欄位級 update 端點**——要推送 lat/lng/level/summary 這類欄位修正，需要新增一個 update endpoint。
   - 可能需要一個「只回傳 ID + UpdatedAt 輕量清單」的端點（或讓既有 list 端點支援欄位篩選），支援「二、傳輸流程」三層比對中的第一層；`pull` 情境下，這個清單改由本機把自己的清單送給正式站，而非正式站提供端點讓本機查詢，兩個方向的端點形狀不同。
   - 交握式傳輸本身也需要新的端點/協定支援逐筆傳送＋逐筆回報寫入結果（見「二、傳輸流程」的交握協定）——目前完全沒有對應機制，屬於全新設計。
   - **比對邏輯需抽成兩邊 server 共用的套件**（見「三、架構」）：不是新增 endpoint 本身的問題，但會影響這些 endpoint 的實作方式——`push`/`pull` 各自對應的 handler 應該呼叫同一套比對函式，只是資料的取得方向不同（自己查 DB vs. 從請求 body 取得對方送來的資料）。
4. **差異報告的呈現細節**：欄位級差異要顯示到多細（例如浮點數 lat/lng 誤差多少視為「不同」）。
5. **逐筆寫入失敗時的處理**：交握協定中，若目的方某一筆寫入失敗（而非整批中斷），是要中止整個批次等待重試，還是跳過這筆繼續、最後統一回報哪幾筆失敗——目前只確認了「筆數不符就整體重新查詢斷點」，單筆失敗的細部行為待確認。

## 明確擱置、暫不處理的項目

以下項目已討論過方向，但決定先不在這次設計/實作範圍內處理，記錄於此避免之後重新討論：

- **授權範圍/信任邊界**：目前設計是「重用個人登入 JWT 觸發同步」，代表任何完成過 `attraction-sync-setup` 授權的人，之後都能無限次觸發同步、寫入正式站資料，沒有額外的過期/範圍限制。本機是使用者自己的開發機，風險可控，先不處理；若日後這個機制被複製到其他情境（例如 CI），需要重新檢視這個信任邊界。
- **同步審計紀錄**：目前設計中，同步是一次性動作，做完即結束，本機與正式站都不會留下「這次同步做了什麼」的紀錄。若日後需要回溯「這筆資料是什麼時候透過同步寫入的」，現況無法查詢。先不處理。
