# Playwright 走查回饋（2026-08-13）

以 Playwright 模擬一位第一次造訪 tripace 的旅行規劃者，走過首頁 → 註冊 → 建立行程 → 規劃的完整流程後的使用感想與建議。狀態：待處理，尚未排入優先序。

## 走查路徑

首頁 → `.login-form-switch-action` 切換註冊 → 填 email/密碼/暱稱送出 → 建立行程「花蓮三日遊」→ 進入行程 → 輸入一筆記事 → 「規劃」分頁（地圖候選籃）→「推薦景點卡片(試做)」/「推薦景點橫滑(試做)」→「路徑」→「時間軸」。

## 整體印象

首頁的敘事式呈現（京都探索意象、捲動效果）視覺上很有質感，第一眼就能感受到產品定位是「深度探索一個地方」而非傳統列表式行程表。註冊、建立行程的操作路徑都很順——填完 email/密碼、輸入行程名稱後幾乎是即時生效，沒有多餘的確認步驟或轉場延遲。

## 做得好的地方

1. **記事輸入 → 時間軸即時同步**：在下方輸入「6/29 09:00 入住花蓮翰品酒店」後，內容立刻出現在對話串與時間軸中，這種「隨手記、自動排序」的心智模型很直覺，比起手動填表格式的行程輸入更貼近使用者實際規劃時的思考順序。
2. **地圖式候選籃（規劃分頁）**：右側清單卡片、地圖上的「+」加入候選，這個概念本身很好——搜尋地點、瀏覽景點/飯店/餐廳分類、拖進候選籃，一氣呵成。

## 建議與待改進之處

1. **「規劃」地圖沒有跟著行程內容走**：建立的行程叫「花蓮三日遊」，但點開規劃分頁後，地圖預設定位在京都、右側清單也顯示京都景點（清水寺、嵐山竹林小徑等）。這對使用者來說會很困惑——感覺像是規劃內容跟行程本身脫鉤了。建議規劃分頁預設應該根據行程名稱或已輸入的記事（如地點關鍵字）做初始定位，或至少提供清楚的「尚未設定目的地，這是範例資料」提示，避免使用者誤以為系統推薦花蓮景點結果卻顯示京都。

2. **推薦景點卡片／橫滑（試做）兩個面板內容目前完全相同**：兩者呈現的都是京都嵐山周邊的景點卡片，並標示「(試做)」，可以理解這是原型階段功能，但如果最終會保留兩種呈現方式，建議在正式版前想清楚兩者的使用情境差異（例如卡片版適合詳細比較、橫滑版適合快速瀏覽），現在兩個入口內容一致容易讓人覺得是重複功能。

3. **「路徑」面板的定位權限失敗處理**：點開路徑規劃時看到「無法取得目前位置：User denied Geolocation」直接顯示在畫面上，這是無頭瀏覽器環境的預期行為，但作為錯誤訊息呈現稍嫌生硬——建議在使用者拒絕定位權限時，改成更友善的提示文案加上「手動輸入起點」的替代操作引導，而不是直接顯示技術性錯誤字串。

4. **WebSocket 連線異常（技術面觀察）**：瀏覽器 console 中偵測到 `ws://localhost:8080/v1/trips/{id}/ws` 回傳 `501 Unexpected response code`（非本機 onagent 相關的預期連線失敗）。即時協作/多人同步很可能依賴這條 WebSocket，值得請後端團隊確認這條路徑在目前部署下是否應該可用，若這是功能尚未實作，建議前端在偵測到連線失敗時給予降級提示（例如「即時同步暫時無法使用」），而非靜默失敗。

5. **行程列表的「新增行程」互動可以更明顯**：新增行程是透過點擊列表中一個帶「+」圖示的項目、展開成 inline 輸入框完成，這個互動本身沒問題，但初次使用者若沒注意到列表項目本身可以點擊，可能會找不到入口。可以考慮讓這顆按鈕的視覺樣式更突出（例如常駐在列表頂部的獨立按鈕，而非融入列表項目樣式）。

## 小結

核心的「輸入記事 → 自動整理進時間軸」體驗是這個產品最有記憶點的部分，值得持續打磨。目前比較明顯的落差在於「規劃/探索」相關功能（地圖、推薦景點）還停留在展示京都範例資料的階段，尚未真正跟使用者實際建立的行程資料串接——這會是從原型走向正式產品前最值得優先處理的項目。
