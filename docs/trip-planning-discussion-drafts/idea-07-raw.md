### 構想 7：候選點的「就近備胎」——當一個地點臨場崩了，我不會整個下午開天窗（新手旅行者開場）

**新手旅行者**：

前六個構想幫我把行程從無到有排出來了，但我最深的恐懼是排好之後、真正到了當地才發生的事：我照著計畫走到那間查了很久的小店，結果門口貼一張看不懂的紙——臨時公休、裝修、或搬走了。構想 4 的「限制帶」會在排程時提醒我固定的公休日，但它防不了「資料過期」和「臨場突發」：Google 上寫營業中、實際卻拉下鐵門，這對熟門熟路的老手只是聳個肩換下一家，對我卻是整個下午開天窗——我人生地不熟，站在陌生街頭完全不知道方圓五百公尺還有什麼可去。這不是排程階段的問題，是我**站在現場、計畫破一個洞、需要立刻補**的問題，前六個構想沒有一個處理它。

我想要的不是「保證資料永遠正確」（做不到），而是**讓每個排進行程的點，身邊都有一兩個備胎在等著**。具體的形狀：規劃階段當我把一個候選點正式排進某個時段時，系統可以在候選籃裡（構想 1）安靜地替它標一個「就近同類備援」——不是新的推薦流，而是純粹從我**已經看過、暫存過但沒排進去的候選點**裡，挑出地理上就近、類型相近的那一兩個，用一條極淡的虛線把它們跟正式點在地圖上繫在一起。它不佔時間軸的位置、不算移動時間、不進日層架，就只是一個「如果 A 崩了，B 在走路五分鐘外、性質差不多」的臨場保險。這完全複用構想 1 的雙向連動與琥珀 marker，只是多一層「主／備」的視覺繫連，嚴守既有互動姿態：預設不強加，老手完全可以無視，我這種新手才會在出發前特意掃一眼「每個點都有備胎嗎」。

關鍵是它要能**在現場被召喚**。到了當地那間店真的關了，我在時間軸點那張卡，除了現有的導航按鈕，多一個「這裡去不了」的入口，它就地浮出當初繫好的那一兩個備胎（附一句白話「距離約 400 公尺、同樣是拉麵店」），我一按就能把備胎頂替上去、時段沿用。沿用暖色調底部面板即可，不需要新畫面。這樣我在陌生街頭崩潰的那三分鐘，手機直接告訴我往哪走，而不是逼我當場從零重查一個看不懂評論的地方。它填的正是「規劃得再好，臨場一破就全垮」這個新手獨有的、前六構想都沒碰到的脆弱點。

**設計師**：

這個構想的問題意識我完全同意——前六構想全都活在「規劃桌前」，沒有一個真的陪使用者站到那條陌生街上，而「臨場破洞」確實是新手最赤裸的恐懼。但我想對它的**資料來源**與**配對時機**這兩根柱子都動手術，否則它在最需要的那一刻最容易空手。

先講最致命的一點：**只從「自己沒排進去的候選籃」取備胎，在實務上會系統性地失效。** 因為使用者的排程行為恰恰是「把最想去的先排掉」——被留在籃底的，往往是他當初就評價較低、或根本不同類的殘渣。結果是「品質最高的正式點」配到「品質最低的剩菜備胎」，而且愈是規劃認真的新手（把好點都排滿了）愈沒有備胎可繫。這是逆向選擇。所以我主張：籃內同類點是**首選來源**（零成本、使用者已認可、離線可用），但機制必須有**第二層兜底**——在「這裡去不了」被按下的**當下**，才對「這個時段、這個座標」發一次即時的 nearby-similar 查詢。不是規劃期就狂打 API，而是把它設計成 lazy：籃內湊得滿就不查，湊不滿或當場臨時要更多，才即時補。這也順勢回答了老手一定會問的「我籃子空了怎麼辦」。

第二，**「配對在排程時算一次」這件事本身要拆開看。** 我認為該固定的是「**繫連關係**」（A 身邊掛著哪幾個備胎候選——這是使用者規劃意圖的一部分，值得跨 session 保存），該延後的是「**備胎此刻還算不算數**」（它今天開不開、還在不在）。前者出發前算好、離線也在；後者只在「這裡去不了」被召喚的那一秒，才去對備胎本身做一次 live 的營業狀態校驗——避免「翻開保險箱發現裡面那張也過期了」的二次崩潰。把它想成：關係是靜態註記，可用性是臨場刷新。

第三，元件面我的誠實判斷：**大部分是資料註記問題，只有一處是真的新表面。** 地圖上的主／備繫連完全複用 `RecommendedPlacesMap` 既有的琥珀 marker 與描邊分組語彙，那條虛線就是既有連線帶換一種 dash style，不是新機制；時間軸卡片的「這裡去不了」也只是 `PaceRouteMap` 已文件化的「點卡片→地圖平移」互動再掛一個動作。唯一結構性新東西，是**臨場那個暖色底部面板**——它得同時承載「校驗中／備胎清單／一句白話理由／一鍵頂替＋沿用時段」，還要處理「頂替後原正式點降級為新備胎」的資料回寫。這不難，但它是真的新 surface，別假裝能塞進現有卡片。

最後兩個細修。**虛線我保留但要克制**：規劃期預設不畫，只在使用者主動「掃備胎」或 hover 正式點時淡入，否則地圖會被主副線織成蛛網，違反構想 1「只召喚不強加」。**配對基礎不能只靠「同類」**——「拉麵配拉麵」只是起點，得接上構想 4 的限制系統：一個此刻公休、或步行距離其實 1.2 公里（不是文案吹的 400 公尺）的同類點，是壞備胎。排序權重我建議是「同類 × 就近（分鐘制，沿用構想 3 全域規則）× 當下可營業」，而且那句白話理由必須誠實報距離與營業狀態，而不是報一個規劃期算好、早已過期的數字。

**老手旅行者**：

先講一句可能會讓新手意外的話：這個功能對我**同樣有用**，而且我不覺得它冒犯。臨場一家店崩了，我確實會聳肩自己搜——但「自己搜」在異地是有實實在在成本的：我得掏手機、切輸入法、想關鍵字、在一堆看不懂的評論裡目測哪家不是雷、還要心算走過去要幾分鐘。這一整套我做得順，但它照樣吃掉我站在街口的五到十分鐘。如果出發前那條繫連已經幫我把「方圓五分鐘、同類、當下開著」這件事算掉大半，我省的不是「不會找」，是「不用再找」。所以我把它定位成**對兩種人都省事、只是省的東西不同**：新手省的是崩潰，我省的是那幾分鐘的操作摩擦。它不是新手的柺杖，是所有人的臨場保險——這點我要幫設計師把定位說死，免得它被誤當成只服務新手的功能而在取捨時被犧牲。

但設計師那個「壞備胎逆向選擇」，我要修正一半。**認真的老手不會把好點全排滿。** 我排程時本來就會刻意留兩三個強候選不排進時段——不是懶得排，是我知道現場一定有變數，這幾個是我主動留的彈藥。所以對我而言籃底不是殘渣，是我**故意存的備援**。設計師描述的失效模式對「把好點全塞滿的認真新手」成立，對我不成立。這帶出一個具體提煉：機制別假設籃底品質一律低，而該讓使用者能**主動把某個候選標成「留作備援」**——被標的點在配對時權重加成，也不會被日層架的粗傾倒草稿掃進某一天。這樣新手靠 lazy live 兜底、老手靠「刻意留彈藥」，同一機制兩種餵法，跟構想 1「兩種姿勢」一脈相承。

最後是我最不安的一點，得替現場的人講：**設計師的 lazy live 查詢，在最需要的那一秒最可能靠不住。** 異地漫遊、地下街、山區、境外 SIM 塞爆——我站在拉下鐵門的店前、正焦躁，這時候還要等一個 live nearby 查詢轉圈、甚至轉不出來，那是雪上加霜。所以我的立場很硬：**繫連關係與「上次已知可用的備胎清單」必須離線就在手上**，live 校驗是「有網就加分、沒網不致命」的增強，不是召喚的前提。按下「這裡去不了」，先秒開離線那一兩個備胎（誠實標「營業狀態為出發前資料」），live 校驗在背景跑、回來了再靜靜更新綠燈或劃掉——絕不能是「先轉圈、查到才給看」。這跟設計師說的不完全衝突，但**優先序要顛倒**：先給離線的、可能不完美的，勝過讓現場的人空等一個可能永遠不回來的完美查詢。

一句成本提醒收尾：這是「以防萬一」功能，但破洞在異地是**高頻**事件（資料過期、臨時公休比想像常見），值得建；只是務必守住設計師「多數是資料註記、只有暖色面板是新表面」的判斷，別讓它膨脹成第二套推薦引擎。我唯一還懸著的真實張力，是「離線優先 vs live 優先」的召喚時序——這點我跟設計師之間還沒完全對齊，留給仲裁者定奪。

**設計師（收斂回應）**：

老手這一刀切得對，我全盤收下——把優先序顛倒，離線優先、live 第二。我原本的 lazy live 是「省 API 成本」的工程直覺，但站在拉下鐵門的店前，那個直覺剛好把風險堆到最脆弱的一秒。改正：**繫連關係與備胎的「上次已知狀態」快照，在配對成型的當下就寫進裝置本地快取**，出發前、離線、漫遊塞爆全都在手上。刷新採機會主義——有網就趁規劃期、趁背景時機悄悄更新，沒網就守著上次的。按下「這裡去不了」永遠是**秒開離線那一兩個備胎**，live 校驗降級為非阻塞的背景增強：回得來就靜靜把狀態更新成綠燈或劃掉，回不來也不影響使用者已經拿到的答案，絕不轉圈空等。

**「上次已知狀態」怎麼顯示，是誠實與否的關鍵。** 尚未經過近期 live 確認的備胎，狀態旁掛一個克制的**新鮮度註記**——「營業狀態為上次規劃時資料」的淡字，而非綠燈；等背景 live 校驗回來，才升級成確認態的即時綠燈（或劃掉並補一句原因）。使用者永遠分得清「這是舊資料的樂觀」與「這是剛剛確認的」，不會被一個過期綠燈二次騙進另一扇鐵門。

**「留作備援」機制我正式收進來**，這補上我逆向選擇論證的另一半。使用者可主動把某個沒排進時段的強候選標成「備援」：被標的點在配對時權重加成，**並且排除於構想 3 日層架的粗傾倒草稿**——它不會被自動掃進某一天而意外排掉。於是新手靠背景 live 兜底、老手靠「刻意留彈藥」，同一機制兩種餵法，跟構想 1「兩種姿勢」一脈相承。

其餘維持我上一輪的定案：配對基礎是「**同類 × 就近（分鐘制，沿用構想 3）× 已知營業狀態**」，那句白話理由誠實報最後已知的距離與營業狀態、並標明資料時點；虛線視覺**克制**——規劃期預設不畫，只在主動「掃備胎」或 hover 正式點時淡入，不讓地圖被主副線織成蛛網。暖色底部面板仍是唯一真正的新表面，其餘皆為既有元件的資料註記。

**構想 7 的最終定義**：構想 7 為每個排進時段的點掛上「就近同類備胎」，把前六構想全都停在「規劃桌前」的盲點延伸到使用者真正站上陌生街頭、計畫破洞的那一刻。它對新手（省崩潰）與老手（省重查的操作摩擦）同等有用，定位為所有人的臨場保險而非新手柺杖。資料採**離線優先、live 第二**：繫連關係與備胎的上次已知狀態快照在配對當下即寫入本地、離線恆在，有網時機會主義地背景刷新；按下「這裡去不了」永遠秒開離線備胎，live 校驗僅為非阻塞的背景增強，未經確認的狀態以「上次規劃時資料」的克制新鮮度註記呈現、確認後才升級為即時綠燈。配對基礎為「同類 × 就近分鐘 × 已知營業狀態」，並接上構想 4 的限制系統剔除壞備胎；使用者可主動把強候選標成「留作備援」以加成配對權重並排除於構想 3 的粗傾倒草稿。視覺上完全複用構想 1 的雙向連動與琥珀 marker，僅多一層克制、只召喚不強加的主／備虛線繫連，唯一結構性新表面是承載召喚、頂替與時段沿用的暖色底部面板。

## 仲裁判定（主代理）

**判定：達成共識。** 功能定位（新手省崩潰、老手省摩擦，非新手專屬）三方一致；設計師指出的「逆向選擇殘渣」問題與唯一真實張力（lazy live 查詢 vs 離線優先）由仲裁者裁定採用老手的優先序反轉：繫連關係與上次已知狀態在配對當下就寫入裝置本地、離線恆在，「這裡去不了」永遠秒開離線備胎，live 校驗只是非阻塞背景增強。老手新增的「留作備援」明確標記機制（加成配對權重、排除於構想 3 日層架粗傾倒）一併正式採納，同時解決了逆向選擇問題（認真規劃者可主動保留強候選當彈藥，不必依賴籃底殘渣）。設計師已將裁定轉譯為最終規格。已寫回主文件正式結論，見 `docs/trip-planning-design-discussion.md` 構想 7。
