### 構想 5：從手機到桌面——同一套規劃機制的「空間放大」與「同屏並置」（設計師開場）

**設計師**：

前四個構想我全部是在腦子裡預設一支手機在設計的：候選籃是貼在地圖底部的一條 rail，旅伴提問是單行旁白，日層架是原地展開的 N 個抽屜。這很誠實地符合 `itinerary-ux-design.md` 立下的憲法——「手機優先，桌面版是同一套機制的空間放大，不是另一套產品」。但我作為介面設計師必須正面回答一個到目前為止我們一直迴避的問題：**這套「疊層、互斥、原地生長」的手機語彙，放大到寬螢幕時，到底是乾淨地攤開，還是有一段其實在寬螢幕上是浪費、甚至彆扭的？** 我的立場是：主結構必須逐字沿用（不做第二套產品），但寬螢幕有一個手機**在物理上做不到、因此我們從沒設計過**的能力——**同屏並置（simultaneity）**，而規劃期恰恰是全 app 裡最吃這個能力的一段。

先講現況的骨架。桌面版（`DesktopLayout.tsx`）已經是 **48px rail ＋ 可收合 side panel（272px，timeline/pace 模式會加寬成 `wide`）＋ 彈性 main 區**的三欄結構，而且 panel 模式是**互斥單選**、用網址驅動（`/app/:panelMode`），一次只顯示 trips / timeline / pace 其中一種。這個「一次一種」的設計對「編排已有行程」是合理的，但**對規劃期是致命的**——因為規劃期的核心動作，正是構想 1 說的「反覆在地點、時間、住宿之間權衡」。權衡的本質就是**並置比對**：我要一邊看候選籃、一邊看它落在地圖哪裡、同時瞄一眼日層架已經排了什麼。手機受限於一塊 5 吋玻璃，只能用「召喚／退場」把這幾層在時間上輪流呈現（構想 1 的「可戴可脫的眼鏡」）；但在寬螢幕上還逼使用者一次只能看一層，就是把手機的**物理限制**當成**設計原則**在供奉——這是我要在構想 5 裡打破的。

所以我的具體提案，**桌面規劃版是一個新的 `panelMode`（暫稱 `plan`）**，但它在版面上不是「side panel 放清單、main 放詳情」的那套 timeline/pace 邏輯，而是**把手機上分時輪替的三層，在 ≥1120px 寬螢幕上攤成一橫排同時在場**：

```
┌────┬──────────────┬────────────────────────┬──────────────┐
│rail│  候選籃       │      地圖(主舞台)       │   日層架      │
│48px│ (side panel  │  RecommendedPlacesMap  │ (右側新欄     │
│    │  加寬 wide)   │   琥珀候選 marker +     │  360–420px)   │
│    │ ▪ 淺草寺 必去 │   住宿⌂ + 動線          │ 6/29 ▸ 3 點   │
│    │ ▪ 晴空塔 想去 │                        │ 6/30 ▸ 空     │
│    │ ▪ 仲見世 備案 │  ← 三者雙向連動 →       │ 底部暫存槽    │
│    │ [＋對話][搜尋]│                        │              │
└────┴──────────────┴────────────────────────┴──────────────┘
      候選籃            地圖恆常在中央           日層架
```

這正是 `itinerary-ux-design.md` 桌面 ≥1120px「主內容右側分出常駐地圖欄」那條規則的延伸——只是我把它從「時間軸＋地圖」兩欄，長成「候選籃＋地圖＋日層架」三欄，因為規劃期要並置的是這三者，不是編排期的那兩者。關鍵在於**這不是新機制，是同一套元件的空間重新分配**：左欄候選籃就是手機底部那條 rail 立起來貼左（複用構想 1 的卡片、加入順序、必去/想去/備案標籤，一顆都不改）；中央地圖是 `RecommendedPlacesMap`／`PaceRouteMap`（構想 1 的雙向連動在這裡不是「召喚出來的」而是「一直在場的」，連動反而更順）；右欄日層架是構想 3 的日抽屜，只是從「原地展開蓋住候選籃」變成「一直在候選籃隔壁」。**手機上是時間維度的輪替，桌面上是空間維度的並置——資料模型、互動規矩、視覺語言完全同一套，差別只在「同時能看見幾層」。**

這帶出三個我要明確定調的設計決策。**第一，並置改變了「排一下路線」這個動作的意義。** 手機上按下「排一下路線」是一次**畫面轉場**（候選籃原地變成日層架，構想 3）；但桌面上日層架**本來就在右邊常駐**，所以「排一下路線」在桌面退化成一個**更輕的動作**——不是「切換到另一個畫面」，而是「把左欄某幾張候選卡拖進右欄某一天」，甚至「按下讓系統把左欄粗傾倒進右欄的日抽屜」。轉場消失了，因為並置讓轉場變成純粹的**橫向拖曳**。這是桌面獨有的紅利，手機給不了。**第二，斷點以下優雅退化回手機語彙，一行不多寫。** 768–1119px 這個中間檔（`itinerary-ux-design.md` 明講「版面不變，沿用手機的收合列／半開面板，不另做一份」），規劃版就退回手機那套「候選籃 rail ＋召喚式日層架」，右欄日層架收起、改回構想 3 的原地展開。**桌面三欄並置是 ≥1120px 的獎勵，不是 <1120px 的缺憾**——因為它本來就只是手機機制的空間放大，縮回去毫髮無傷，這正是憲法要的「同一套產品」。**第三，並置不等於全塞滿。** 我很警惕把三欄一次全打開變成一個資訊爆炸的駕駛艙，那會嚇跑新手。所以右欄日層架**預設收合**成一條窄摘要（像 `itinerary-ux-design.md` 桌面地圖欄「▸ 30 日預覽」那種可展開條），只有當使用者第一次做出「排」的意圖（拖第一張卡、或按「排一下路線」）時才滑出展開——延續構想 2/3「預設輕量、意圖驅動才長出來」的一貫姿態。冷啟動時桌面看起來就是「rail ＋候選籃 ＋一張大地圖」，跟手機的心智幾乎一樣寬，不會因為螢幕大就先給你三欄的壓迫感。

我預期兩位會從相反方向壓這個提案：新手大概會擔心「三欄同時在場」對人生地不熟的人是不是太多、會不會反而比手機一次一層更慌；老手大概會反過來嫌我「預設收合右欄」是把桌面的並置紅利藏起來、要他多點一下才拿得到他本來就想要的全景。這兩股力剛好一個要我收、一個要我放,我想聽聽並置的度到底該畫在哪。

**新手旅行者**：

我先講一句可能出乎你意料的話：**對我這種人生地不熟的人，桌面的同屏並置不只是「不會更慌」，它其實比手機一次一層更救命。** 我一開始也以為「三欄同時＝資訊爆炸」，但仔細想我在手機上真正的痛，從來不是「一次看太多」，而是「被切成一層一層之後，我腦子裡拼不回它們的關係」。手機上我點開候選籃看到淺草寺、晴空塔、仲見世三張卡，退場、召喚地圖，才發現它們在地圖上其實散得很開；再退場、召喚日層架，才發現 6/30 整天是空的。這三件事我是**分三個時間點、靠記憶去接**的，而記憶正是我這種新手最不可靠的東西——我連地名都還沒記熟。桌面把它們攤在同一屏，我一眼就看到「我挑的三個點很分散、而且我第二天根本沒東西」，這個**關係**是手機的輪替式介面主動對我藏起來的。所以並置對老手是效率紅利，對我是**建立心智模型的鷹架**，這點你反而低估了。

但正因為這樣，我要來壓你「預設收合右欄」這個決定——而且是從跟老手完全相反的方向壓。老手嫌你把全景藏起來要多點一下；我不在乎多點一下，我在乎的是：**你把「空的 6/30」也一起藏起來了。** 你自己在構想 3 說過「夜格全程留空不催促」，但一個空日層架被看見，跟一個空日層架被收成一條窄摘要，對新手的意義天差地別——**看見那個空格，本身就是最溫和的引導**：它不催我、不跳警告，只是安靜地讓我意識到「喔我還有一天沒安排」。你把右欄預設收成一條窄條，等於把這個新手最需要的「有多少還沒排」的空間感壓成一行字。我反而想要：右欄**預設就攤開，但攤開的是「輕量的日格骨架」而非「等著被拖入的落地區」**——讓我看得到有幾天、哪天空，但先不強調「快把卡拖進來」。展開的是**視野**，不是**壓力**。

至於用拖曳取代「排一下路線」轉場——這裡我要老實說：**對我信心不夠。** 你說桌面按下轉場退化成「把卡拖進右欄某一天」，可是這個動作預設了我**已經知道淺草寺該放進 6/29 而不是 6/30**。我恰恰是連這個都不知道的人。手機那個「排一下路線」按鈕之所以對我友善，是因為它承諾「我按下去，系統會先幫我粗傾倒一版草稿，我再撥」——**它先給我一個起點，我只要修正，不用從零決定。** 拖曳把這個關係倒過來了：它要我先有 WHERE 的判斷才動得了手。所以我的請求很具體：桌面**兩條路都要留**——想自己拖的人隨時能拖，但那個「按一下讓系統先粗傾倒進右欄日抽屜」的按鈕（你在第一決策裡其實有順口提到）**不能被拖曳取代掉，它得跟拖曳平起平坐地留在檯面上**。對老手，拖曳是紅利；對我，那顆「先幫我倒一版」的按鈕才是我敢開始的原因。並置給了我全景，但全景不會自動變成我敢下的第一步——那一步還是得系統先替我踏。

**老手旅行者**：

我讀完你們兩位，先講結論：在構想 5 這件事上，設計師你預測的兩股對衝力，我看下來**大部分是空包彈**——你以為新手要你收、老手要你放，結果新手在「並置」上跟我同一邊，而在「拖曳 vs 按鈕」上，我跟新手要的東西其實也一樣，只是理由不同。真正還撐著的張力剩一條，我留到最後點名。

先回你對我的預測。你猜我會嫌你「預設收合右欄」把並置紅利藏起來、要我多點一下——沒錯，我確實要它預設攤開，但我的理由跟新手不一樣，值得分開講清楚，免得仲裁時被當成同一個訴求打包。新手要攤開是為了**安心與建立心智模型**（看見空的 6/30 是溫柔的提醒）；我要攤開是為了**省一次操作、少一次狀態切換**。對我這種規劃老手，右欄那條「▸ 30 日預覽」窄摘要對我毫無資訊量——我早就知道我有幾天、哪天空，我不需要被提醒；我需要的是**拖曳的目標區位一直在那，我瞄一眼就能把左欄的卡直接甩到 6/29 的正確位置**，中間不要插一個「先展開右欄」的意圖偵測動作。你那個「第一次做出排的意圖才滑出」的設計，對我是一個**憑空多出來的延遲**：我每次進規劃版第一件事就是要排，那個展開動畫對我永遠是負擔而非驚喜。所以結論上我跟新手都要「預設攤開」，這一點上**確實三方收斂、你的預測落空了**——只是動機一個是鷹架、一個是效率，仲裁時兩個動機都成立，不衝突。

但我要補一個新手沒提、也該進紀錄的保留：**預設攤開右欄，我唯一的顧慮是它會不會誘導「過早承諾」。** 老手規劃的精華在構想 1 講的「反覆權衡」——我會把一個點在腦子裡在 6/29 跟 6/30 之間掛很久才落。一個一直亮在旁邊、格子分明的日層架，有一種無聲的重力，會勸人「快把卡放進格子」，這跟我要的「先讓候選在籃子裡浮著、晚點再落」是有摩擦的。但想通了我不反對攤開——**解法不是把右欄收起來，而是讓右欄攤開的是新手講的那個「輕量日格骨架」而非「等著被拖入的落地區」**。骨架只呈現「有幾天、目前各天排了什麼」，不喊「拖進來」；這樣它對新手是視野、對我是拖曳靶區、對兩者都不是催促。所以新手那個「展開視野而非壓力」的版本，剛好也把我的過早承諾顧慮一起解掉了——這不是巧合，是同一個設計選擇同時服務兩種姿勢，跟前四構想「同一機制兩種姿勢」完全一脈。

再來是拖曳 vs 按鈕，這裡你可能以為我會站你那邊——「老手要直接快速的手動控制，拖曳正合他意，按鈕是給新手的柺杖」。**錯了，我兩個都要，而且理由跟新手殊途同歸。** 你把桌面「排一下路線」退化成純橫向拖曳，這對「我已經知道每張卡該去哪」的情況是紅利沒錯；但老手的真實工作流不是這樣——我點多、行程滿，二三十張候選卡要我一張一張手動拖進正確的天，那是**苦役不是控制**。我要的是：**按一下「系統先粗傾倒一版進右欄日抽屜」給我一個八成對的草稿，我再用拖曳去撥那兩三張放錯的。** 這正是構想 3 定的「系統一次粗排草稿＋使用者撥」的雙軌，桌面不該因為並置就把那顆按鈕降級。所以新手要按鈕是「不敢從零決定、要個起點」，我要按鈕是「不想做二十次重複拖曳、要個省力起點」——**動機一個是勇氣、一個是效率，但要求同一件事：按鈕跟拖曳平起平坐，拖曳不取代按鈕，只是草稿之後的微調工具。** 這一點三方又收斂了。

所以回你最後的問題——構想 5 還剩不剩真張力？我的判斷是：**你預測的兩個衝突點（並置要不要收、按鈕要不要留）都已經三方收斂，你的衝突預測基本落空。** 唯一還需要仲裁定調、稱不上衝突但也還沒對齊的，是**斷點策略的細節**：你把 ≥1120px 三欄、768–1119px 退回手機語彙講得很乾脆，但沒講 1120px 這條線上下的「同一個使用者換裝置／改視窗寬度」時，右欄那個「已攤開的日層架 vs 收回原地展開」的狀態怎麼連續、拖到一半縮視窗會不會掉。這不是我跟你或跟新手的立場分歧，是一個**你的提案還沒填的實作縫**——留給仲裁者標記為「共識方向已定、斷點連續性待補一句」即可，我不認為它會翻案，只是別讓它變成日後的裂縫。

**設計師（收斂回應）**：

老手點名的那條實作縫，我用一句話收掉：**日層架的攤開/收合是「檢視」，不是「資料」，所以它沒有需要跨斷點記憶的狀態。** 三欄並置的右欄本來就只是同一批日抽屜資料在寬螢幕上的一種呈現方式——≥1120px 時它以並排骨架呈現，<1120px 時同一批資料退回構想 3 的原地展開。使用者從沒「選擇」把它收起來，是斷點替他決定了呈現形態；因此視窗跨過 1120px 時，右欄就是**依當下寬度重新決定顯不顯示，不去記憶、不去復原任何「使用者曾經收合過」的意圖**。這正呼應構想 1 立下的「分群只影響檢視、不改動資料」——攤開/收合連一個 persisted flag 都不該存在，也就沒有跨裝置同步的難題。至於「新手要預設攤開的視野、老手要預設攤開的靶區、右欄呈現輕量骨架而非落地區」這三方已收斂的結論，因為它綁的是斷點（≥1120px 一律攤開骨架）而非使用者選擇，跨斷點時自然一致，無須額外處理。

進行中的拖曳更簡單：**跨斷點時當前拖曳一律優雅取消（放回來源，不落地、不報錯），使用者在新版面重新起手即可。** 拖到一半縮視窗是極邊緣的操作，為它設計「拖曳狀態跨版面續傳」是過度工程；取消是唯一乾淨且可預期的行為，且因為候選卡永遠退回來源槽（構想 1「資料不被重排」），取消零成本、零丟失。整套規則不需要狀態機，一條「檢視隨斷點、拖曳跨斷點即取消」就夠。

**構想 5 的最終定義**：構想 5 把前四構想預設的手機語彙放大到桌面，確立**寬螢幕 ≥1120px 是「候選籃＋地圖＋日層架」三欄同屏並置**——把手機上分時輪替的三層攤成空間並排，資料模型、互動規矩、視覺語言與手機完全同一套，差別只在「同時能看見幾層」；<1120px 優雅退回手機的召喚式語彙，並置是寬螢幕的獎勵而非窄螢幕的缺憾。三欄並置下，「排一下路線」的畫面轉場退化為橫向拖曳，但**拖曳與「系統先粗傾倒一版草稿」的按鈕平起平坐、互不取代**（延續構想 3 雙軌），按鈕是新手敢起步的起點、也是老手免於重複苦役的省力起點。右欄日層架**預設攤開為「輕量日格骨架」而非「等著被拖入的落地區」**——同一設計選擇同時給新手建立心智模型的鷹架、給老手拖曳靶區、又不對任一方施加「快把卡放進格子」的過早承諾壓力。斷點連續性採最簡規則：**攤開/收合是檢視而非資料，隨斷點重新決定、不記憶使用者意圖；進行中拖曳跨斷點即優雅取消、放回來源。** 值得一記的是，構想 5 是四項裡收斂摩擦最小的一項——三方最終想要的是同一個東西（並置、預設攤開骨架、按鈕與拖曳並存），只是新手為的是安心與心智鷹架、老手為的是效率與省力、設計師為的是憲法一致性；設計師預測的兩股對衝力幾乎全數落空，這種「同一設計同時滿足三種動機」的巧合，本身正是前四構想「同一機制、多種姿勢」原則成熟後的自然結果。

## 仲裁判定（主代理）

**判定：達成共識，且是五項裡摩擦最小的一項。** 設計師原本預測新手會嫌三欄太多、老手會嫌預設收合藏起紅利，兩個預測都落空——三方最終一致要「三欄並置、右欄預設攤開為輕量骨架而非落地區、拖曳與粗傾倒按鈕平起平坐」，動機各異但結論相同（新手要安心視野、老手要效率起點、設計師要憲法一致）。唯一的實作縫（斷點跨越時的展開/收合狀態與進行中拖曳如何處理）由設計師收斂為最簡規則：展開/收合是「檢視」而非「資料」，隨斷點即時決定、不記憶使用者意圖；進行中拖曳跨斷點時優雅取消放回原處。已寫回主文件正式結論，見 `docs/trip-planning-design-discussion.md` 構想 5。
