# override.md

補充 SKILL.md「判斷是否破壞性」的規則，不取代原本的判斷方法，只是額外釐清一種容易誤判的情況。

## CLI 介面才是破壞性判準

本專案的公開介面是 **CLI 子命令的呼叫方式**（旗標名稱、必填/選填、輸出格式），不是它底層打的內部 API 端點本身。

判斷是否破壞性時：

- **CLI 子命令的呼叫方式有更動**（新增/移除/改名旗標、改變必填規則、輸出格式不相容）→ 破壞性，按 SKILL.md 既有規則升版。
- **CLI 底層呼叫的內部端點（`/internal/*`，需登入）回應形狀改變，但 CLI 呼叫方式本身不變、且呼叫端在同一次異動中同步更新** → 不算破壞性。這類端點只給自家前端/CLI 用，不是對外公開的相容性承諾對象，即使回應 JSON 結構改變，也不會讓任何外部呼叫端「打新版端點壞掉」——因為外部本來就打不到、也不該打這些端點。

判斷順序：先看有沒有動到 CLI 子命令本身的呼叫方式；沒有的話，即使底層端點/資料結構有變動，也先當作非破壞性處理，除非另有明確理由（例如該端點其實有外部呼叫端、或改動影響到資料正確性而非單純形狀）。

## 刪除整項正式功能也算破壞性

跟 CLI 介面判準是分開獨立的規則：若這次異動**整個移除**一項使用者已經在用的正式功能（不是試做/demo/預設關閉的 feature flag 項目），即使沒有任何 CLI 旗標或公開符號被改動，仍算破壞性——使用者可感知到的能力消失本身就是相容性斷裂，不需要靠符號層級的變動才成立。

判斷「正式功能」的方式：功能本身有沒有預設對一般使用者開放（不是藏在 `DEMO_*_ENABLED` 這類預設關閉的旗標後面）、使用者是否已經有機會依賴它。試做/實驗性/預設關閉的功能被移除或調整，不算破壞性。

## 前端內部元件的公開符號變動，不套用 SKILL.md 的符號層級判準

跟前面幾條一樣是分開獨立的規則：`web/src` 底下的 React 元件 props、內部函式簽名、型別定義，都是這個應用程式自己的實作細節，不是給其他專案/套件使用者引用的公開 API——SKILL.md「有公開符號被移除/改名，即為破壞性，不論改動規模大小」這條規則是針對函式庫/套件語境設計的，不適用於這個應用程式的前端程式碼。

判斷前端改動是否破壞性，一律看**使用者實際感知到的行為/功能**，不看程式碼符號本身：

- **移除/改名一個 React 元件的 prop、內部 hook 的回傳欄位、純前端型別欄位**，只要呼叫端在同一次異動中同步更新、且使用者操作起來的功能/行為沒有減少或改變成不相容的樣子 → 不算破壞性，即使那個 prop 曾經是必填。
- **UI 文案調整、視覺呈現方式改變（如按鈕文字拿掉變數插值、清單改成收合摺疊呈現）** → 不算破壞性，屬正常的 UI 迭代。
- **拿掉使用者原本能做到的一項操作/能移除一個可見的功能入口** → 才算破壞性，判準與上面「刪除整項正式功能」那條一致。

判斷方式：問「使用者從畫面上操作，會不會發現自己少了一項原本能做的事，或原本的操作方式行不通了」——不會的話，即使 TypeScript 介面（props/型別）確實變小了，仍當作非破壞性處理。

## 資料表變更需要人工介入時也算破壞性

跟前兩條分開獨立的規則：資料庫 schema 變更若無法只靠 `AutoMigrate` 自動、無痛套用，即算破壞性，不論有沒有動到 CLI 介面或移除功能：

- **新增資料表/欄位，但既有資料列需要回填（backfill）才能讓新功能正確運作**（例如新增一個 `NOT NULL` 欄位、或新功能依賴某個欄位對舊資料有值）→ 破壞性。單純新增一個允許 `NULL`/有預設值、且沒有既有資料需要回填的欄位，`AutoMigrate` 能無痛處理，不算。
- **刪除資料表/欄位** → 破壞性，即使 `AutoMigrate` 本身不會主動刪除（GORM 的 `AutoMigrate` 預設不刪欄位/表），只要程式碼邏輯上已經不再讀寫某個現存欄位、或需要手動下 migration 刪除，都算——資料遺失風險或需要人工判斷「這個欄位還能不能刪」本身就是破壞性訊號。
- **`AutoMigrate` 無法直接套用、需要手寫 migration script 或人工介入資料庫** （例如改欄位型別、加索引到已有大量資料的表可能鎖表、調整主鍵）→ 破壞性。

判斷方式：問「這次的 schema 變更，能不能讓 `AutoMigrate` 自動跑、不用人工看一眼資料庫現況就安全套用到正式環境」——不能的話就算破壞性，不論是否對外公開。
