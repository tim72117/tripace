# frontend-design-guidelines

做前端 UI 相關的新增/修改時,依下列面向自我檢查,而不是只求「能動、看起來過得去」。這份清單刻意不放具體風格數值(色票、字級、圓角半徑等)——那些屬於這個專案既有的視覺語言,做之前應該先讀既有元件/CSS 變數,照現有慣例走,而不是套一份寫死的規範。

另見同目錄下的 [PITFALLS.md](PITFALLS.md)——實際發生過的具體錯誤案例清單(如 IME 組字誤觸送出),動手前一併查閱,避免重蹈覆轍。

## 一致性

- 動手前先找一個功能相近的既有元件當參照,而不是憑空設計——顏色、間距、圓角、陰影都應該來自既有的 CSS 變數/既有樣式,不手寫新的數值。
- 同一組互動(例如「加入候選」「移除」「展開/收合」)在不同畫面該長一樣,不要因為換了個元件檔案就重新發明一套視覺語言。
- icon 庫、命名慣例(CSS Modules class 命名、變數命名)跟著專案既有規則走。

## 狀態要看得見

- 每個互動元素至少要有 hover/active/disabled/loading 這幾種狀態的視覺回饋,不能只做「靜止」跟「點下去有效果」兩種。
- 可點選的元素(按鈕、可點卡片、role="button" 的 div 等)要有 cursor: pointer;停用時要有 cursor: not-allowed 且視覺上明顯不可互動;純展示、不可點的元素不要誤設 pointer,避免使用者誤以為能點。
- 選中態、進行中態(如查詢中)要有明確樣式,不能只靠使用者記憶「我剛剛點了什麼」。
- 空狀態(查無資料/清單是空的)要有文字或視覺提示,不要留一片空白讓人以為壞了。
- 錯誤要說清楚發生了什麼、使用者能做什麼,不是單純吞掉或跳一個模糊的提示。

## 版面與留白

- 用 flex/grid 的 gap 控制間距,不要疊加多層 margin 導致間距失控或塌陷。
- 檢查是否有元素互相重疊、或在較窄寬度/內容較長時被裁切——尤其固定定位(position: absolute/fixed)的浮動元件,要確認跟其他浮動元件、跟捲動內容的相對關係。
- 文字過長時要有省略號/換行策略,不能假設內容永遠是短的。

## 可及性(a11y)

- 可互動元素要能被鍵盤操作(tabIndex、onKeyDown 對應 Enter/Space),不是只綁 onClick。
- 圖示型按鈕要有 aria-label/title,純裝飾用的 icon 加 aria-hidden。
- 顏色不是唯一的資訊載體(例如選中態不能只靠顏色變化,搭配邊框/圖示等第二種線索更保險)。

## 動效與回饋節奏

- 動畫是否服務於理解(例如提示「這是新加入的」「這裡展開了」),而不是為了炫技。
- 尊重 prefers-reduced-motion,不強迫所有使用者接受動畫。
- 查詢/儲存這類非同步動作,要讓使用者感覺到「系統正在處理」,避免點下去像沒反應。

## 響應式與斷點

- 確認在專案既有斷點(桌面版/手機版)下都測試過,不是只看單一視窗寬度。
- 桌面版新增的浮動元件、side panel 等,收合/展開時要考慮跟其他區塊的空間互斥或重疊問題。

## 動手前

- 先問:這個畫面/元件的「唯一任務」是什麼?新增的視覺元素有沒有在跟既有的其他重點搶注意力。
- 若同一個資料在多處呈現(例如清單卡片 vs 地圖 marker),想清楚兩者該共用哪些視覺語意(例如同一個顏色代表同一件事),不要各自發明。
